# uir — agent notes

Shared ways of working, the gavel todo workflow, and global skills come from the root `~/.agents/AGENTS.md`.

## What this repo is

The canonical UIR model, extracted from `arch-unit/models/uir`. `arch-unit` still carries its own copy; nothing imports this module yet. Rewiring arch-unit's 89 importing files onto `github.com/flanksource/uir` is a separate, deliberate follow-up that needs this module published first.

## Layout rules

- `Pretty()` and `Hash()` are part of the `Node` interface, so their implementations are locked to the package that declares the node types. Rendering and hashing cannot move to subpackages; only consumers of `Node` can.
- `diff/` and `render/` are the two things that legitimately live outside the root package — both only consume `Node`, neither is imported by it. Keep it that way; a new subpackage is only viable if the root package never needs to reference it.
- `NodesOf[T Node]` in `nodes.go` is the single widening helper. Do not reintroduce per-type `nodesFromX` converters.
- `schema/uir.schema.json` is generated by `make schema` (`cmd/genschema` over `internal/schemagen`) and must never be hand-edited. `internal/schemagen` is the third package outside the root, and like `diff/` and `render/` it only consumes the root package. It derives the node and statement unions from the `uir.Nodes` and `uir.Statements` registries and the enums from the package's typed string constants, so registering a type or adding a constant is the whole change — there is no list to update.

## Deliberate exclusions

These were left in arch-unit on purpose — do not "restore" them:

- `cel_test_helpers.go` (`EvalAssertions`, `AddAssertionIndex`). Keeping it would make `gomplate/v3` and `cel-go` compile-time dependencies of every consumer, for two functions.
- `python/extractor.go` and `python/extractors/`. Extractor tooling, not model; its `init()` wrote to `$HOME/.arch-unit`.
- `json_polymorphic.go` (`PolymorphicRegistry`). Dead duplicate of `registry.go`; nothing referenced it.

The Python model is pure stdlib — it has no `requirements.txt` or `Pipfile` by design. `sqlglot` and `pex` were extractor dependencies.

## Verification

`make build`, `make lint` (must be 0 issues) and `go test ./...` are the gates. A model change that is not followed by `make schema` fails `TestSchemaIsUpToDate`; the same package also checks that the schema accepts what the model actually marshals, which is the part reflection alone cannot guarantee given `MarshalStatement` and `BlockStmt.MarshalJSON` write keys no struct field declares. The Python port is covered by `cross_language_test.go`, which shells out to `python3 python/test_uir.py` and unmarshals the result into the Go types — so a change to either side that breaks the shared JSON shape fails the Go suite.

The `java/` tree is source only, with no build file, exactly as it was in arch-unit. It is not compiled by CI.
