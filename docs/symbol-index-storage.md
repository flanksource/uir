# Snapshot-aware symbol index: schema review

**Status:** Implemented. The schema is created by migrations [`04_module_roots.hcl`](../storage/migrations/04_module_roots.hcl), [`05_source_deltas.hcl`](../storage/migrations/05_source_deltas.hcl), [`06_symbol_index.hcl`](../storage/migrations/06_symbol_index.hcl), and [`07_symbol_handles.hcl`](../storage/migrations/07_symbol_handles.hcl); this document is the design record of that change, which renamed and revised the seven `uir_`-prefixed tables and added four, and of the compact handles that followed it. The [ERD](uir-gorm-erd.tsx) shows the model.

**Compact handles (landed 2026-09-27).** The SHA-256 symbol id is still the identity everywhere outside the database: documents, canonical keys, export shape hashes, input hashes, and every API and JSON result. Inside it, each symbol also has a database-local 64-bit `handle` (`0 | module 11 | package 16 | visibility 1 | kind 3 | local 32`, numbered through the `symbol_modules` and `symbol_packages` registries), and `modules`, `snapshots`, and `documents` have dense database-local `ordinal`s. Postings are keyed by document ordinal, symbol handle, and an integer role, and a new `symbol_deltas` table records per snapshot how its defined-symbol set changed, with shape and body fingerprints. Queries answer "does this snapshot define it" from the deltas and read selector candidates through handle ranges; the diff classifies from the fingerprints and reads only the documents its output needs. A database of the previous generation keeps its registrations and loses its index on open, and `uir reindex` rebuilds it. The tables below describe the landed schema; the evaluation and measurements are in [compact symbol handles and symbol deltas](symbol-compact-ids.md), and the operational detail in the [storage design](../storage/README.md#compact-symbol-handles).

The query syntax in the original design record below has been superseded by the [compact query grammar](query.md).

## Goal and storage boundary

Store, for every indexed file version, one document holding the facts extracted from it: the symbols it declares with their signatures and hashes, the symbols it mentions, and where. When the package type-checks those facts are compiler-proven; otherwise the document holds the syntax-only projection the AST extractor produces today. A reference result must include the source filename and exact range from the selected snapshot. Resolving a symbol's declaration is a second lookup against files active in the selected branch or snapshot, so one symbol identity may have several declaration locations across checkout heads. A diff between two commits must list symbols added, removed, and changed, filtered by visibility, and attribute line additions and removals to file and symbol.

Source bytes remain in Git or the local checkout. The database retains hashes, symbol identities, one document per file version, an inverted index from symbol to the documents that mention it, and per-snapshot symbol deltas. Positions and full per-symbol shape and body hashes live only inside documents; symbol deltas keep a 64-bit fingerprint of each. Historical source viewing and exact line counts require hash-verified bytes; symbol-level facts and reference locations remain queryable when those bytes are unavailable.

The schema uses the repository's portable Atlas HCL subset: `uuid`, `text`, `integer`/`bigint`, `jsonb`, and `timestamptz`; column-based B-tree indexes; primary, unique, foreign-key, and check constraints. PostgreSQL uses those types directly. The SQLite adapter maps them to compatible types and keeps keys and indexes. No view, materialized view, trigger, GIN, trigram, expression index, sequence, or column collation is required, because none of those is portable.

In the tables below, every column is `NOT NULL` unless suffixed with `?`. `PK` and `UQ` each imply an index. All paths are module-relative slash-separated `path_key` values. All line and UTF-16 column numbers are one-based; byte offsets are zero-based, with an exclusive end offset. Every foreign key uses `ON UPDATE NO ACTION`; its `ON DELETE` action is shown with the reference, and unqualified `NO ACTION` means deletion is blocked while a referencing row remains.

Changes from the implemented model: tables renamed; `snapshots` loses `state` and `extractor_version` and gains `worktree_state`, `context_hash`, `coverage`, `package_count`, `diagnostics`, the `(location_id,id)` UQ and two indexes; `location_heads` references the snapshot through its location; `source_revisions` loses `projection` and `extractor_version` and keys the delta and document references by path; `locations` gains a `kind` check and an index. ### Snapshot trigger

Before this design, `indexer/discovery.go` hashed only `.go` files into `ContentSetHash`, and `indexer/modules.go` skipped snapshot creation when revision, content-set hash, configuration hash, and extractor version matched the base. Under that rule a `go get -u`, a `go.work` edit, or an exported-type change in a workspace sibling produces no snapshot and has nowhere to record new facts. Three changes to that seam are part of this design.

1. `ContentSetHash` also covers the dependency manifests: `go.mod` and `go.sum` under their module-relative paths, and the workspace's `go.work` and `go.work.sum` (found through `go env GOWORK`, which may sit above the module) under the fixed keys `go.work` and `go.work.sum`. A dependency bump then yields a snapshot with zero source deltas, which the storage layer already permits.
2. `ConfigurationHash` covers the indexer version and the build variant: `GOOS`, `GOARCH`, build tags, `CGO_ENABLED`, and the Go toolchain version. Exactly one variant is indexed per snapshot; a second variant is a configuration change and a new snapshot.
3. The unchanged check compares `revision`, `content_set_hash`, `configuration_hash`, and `context_hash` (defined below) with the base snapshot. The last catches a workspace sibling whose export shape changed while this module's bytes did not.

`worktree_state` is `clean` when `git status --porcelain` reports no changes under the module and every indexed file is tracked by Git (`git ls-files`), `dirty` otherwise, and `unknown` without Git, in which case `revision` is empty. The tracked-file check matters because discovery indexes `.go` files that Git ignores (a `hack/` directory in `.gitignore`, for example) and `git status` omits ignored files, so without it a snapshot holding files the commit lacks would be recorded `clean`. A commit-to-commit diff must know whether a snapshot's bytes are the commit's bytes.

## Hashes and identities

All digests are lowercase hexadecimal SHA-256 of a versioned, length-delimited canonical encoding.

**Symbol identity.** `symbols.id` digests `(identity_version, module_key, package_path, kind, owner_id, name, ordered parameter type identities)`. `canonical_key` stores that encoding and is unique, so an insert verifies that an existing digest has exactly the expected value. Parameter names, return types, field types, source path, line, and bodies do not enter identity. `module_key` is the Go module path (`root_key` for indexed roots), `std` for the standard library, and empty only for `kind = 'builtin'`. Parameter types use fully qualified named types and recursively encoded composite types; type parameters are encoded by ordinal. Local bindings, parameters, and labels are not canonical symbols: their occurrences stay inside the document with a null symbol, because they are never referenced across files. Canonical identities exist only for typed documents; a `syntax` document's symbol entries carry the v1 `IdentityKey()` and a null id, because unresolved parameter types cannot produce a trustworthy identity.

**Visibility.** A symbol is `exported` when its name is exported and every owner in its chain is exported; otherwise it is `internal`. A method on an unexported type is therefore `internal` even though its name is capitalised.

**Symbol shape.** `shape_hash` digests the symbol's full declared type: the complete signature including parameter names, results, and variadic-ness for functions and methods; the field list with names, types, tags, and embedding for structs; the method set for interfaces; the underlying type for other named types; the type and, for constants, the value for variables and constants. Equal identity and equal `shape_hash` mean the same interface to callers. `shape` is the rendered form for display, in a canonical layout chosen so that two shapes diff line by line: a function or method signature is one line; a struct renders one field per line and an interface one method per line, each line `gofmt`-aligned, between a `type Name struct {` or `interface {` line and a closing `}`; a variable or constant is one line with its type and, for constants, its value. `shape_hash` digests this rendering, so a shape diff never differs from a hash change.

**Symbol body.** `body_hash` digests the token stream of the declaration's extent with comments and whitespace removed. A differing `body_hash` with an equal `shape_hash` is an implementation-only change.

**Export shape.** `export_shape_hash(P)` digests the sorted `(symbol id, shape_hash)` pairs of P's exported symbols together with the sorted `export_shape_hash` of P's direct imports. Because it recurses through imports, a change in any transitively imported exported type changes every dependent's shape. For a package outside the indexed roots it is `H(module path, module version, toolchain version)`; for the standard library it is `H("std", toolchain version)`. Neither requires type-checking the dependency. A workspace package that did not reach `indexed` coverage has no proven shape and therefore no `export_shape_hash`; as an import it contributes a stand-in digest of its file hashes and its own imports' shapes, so its importers still re-extract when it changes, and an import that no module provides contributes its import path. The module's own packages must still be type-checked to compute `context_hash`, so the unchanged decision is cheap only for dependencies; skipping the type-check when the content set, manifests and sibling shapes are all unchanged is a benchmark-step optimization.

**Package input hash.** `input_hash(P)` digests `(configuration_hash, package_path, sorted (path_key, content_hash) of P's files, sorted (import path, export_shape_hash) of P's direct imports)`. Two files of one package share it. It is the complete input to extracting P: same input hash, same document.

**Snapshot context hash.** `context_hash(S)` digests `(configuration_hash, sorted (package_path, input_hash) of every package in the module)`.

**Document key.** A document is identified by `(root_id, path_key, input_hash)`. Since `input_hash` embeds the file's own content hash, the same bytes extracted under a changed dependency get a new document and the old one remains valid for older snapshots.

`symbols` is global and is never cascaded. A symbol with no posting and no symbol delta is unreachable; a future garbage collector deletes such rows with `NOT EXISTS` over the posting and delta indexes, which both lead with the handle. No other retention is proposed, matching the existing policy that snapshots and source revisions are retained.

**Handles.** `symbols.handle` is a non-negative `bigint` laid out most significant bit first as `0 | module 11 | package 16 | visibility 1 | kind 3 | local 32` (`storage/symbolhandle`). The module and package numbers come from `symbol_modules`, which reserves 0 for builtins (`''`) and 1 for `std` because neither has a `modules` row, and `symbol_packages`, which numbers each module's package paths from 0. The local is one past the largest stored handle of its (module, package, visibility, kind) bucket. Handles therefore sort by module, package, visibility, and kind, so "every symbol of a package", "every exported symbol of a package", and "every exported func of a package" are each one inclusive B-tree range. A handle depends on the order symbols were first published, so it is local to one database: it never enters a document, a hash, a canonical key, or a query result. Visibility is part of the handle, so a symbol whose derived visibility changes cannot be re-published under its old handle and fails loudly; a reindex into a fresh database is then required.

**Ordinals.** `modules.ordinal`, `snapshots.ordinal`, and `documents.ordinal` are dense database-local numbers from 1, allocated as one past the current maximum inside the publication transaction; a PostgreSQL publisher that loses an allocation race retries the whole publication, at most three times. Postings and symbol deltas carry the root's ordinal as a plain column rather than through a composite key with the document or snapshot, so the publisher takes it from the row it just wrote.

Coverage has one vocabulary at every level. `indexed`: type-checked without diagnostics. `partial`: type-checked with diagnostics; only proven facts are recorded. `syntax`: the package did not type-check, so the document holds the AST extractor's declarations and unresolved calls, and has no postings. `excluded`: not extracted (build constraints, `testdata`, generated exclusions); the document is empty and says why. A snapshot's `coverage` is the weakest of `indexed`, `partial` and `syntax` among its packages; `excluded` packages do not count unless every package is excluded, and a module with no packages is `indexed`.

### The document

`documents.content` is one JSON object. Its shape is versioned by `indexer_version`, so a format change is a new indexer version and new documents; documents are never migrated in place.

```json
{
  "version": 2,
  "package_path": "example.org/service/invoices",
  "symbols": [
    {
      "id": "3f9c…64 hex…",
      "key": "v1:[\"method\",\"\",\"example.org/service/invoices\",\"Store\",\"Save\",\"\",\"(context.Context,Invoice)->error\"]",
      "kind": "method",
      "visibility": "exported",
      "shape": "func (s *Store) Save(ctx context.Context, inv Invoice) error",
      "shape_hash": "9d2a…64 hex…",
      "body_hash": "c4e1…64 hex…",
      "name": [12, 17, 12, 21],
      "name_bytes": [418, 422],
      "extent": [12, 1, 30, 2],
      "extent_bytes": [406, 902],
      "implements": ["7a10…64 hex…"]
    }
  ],
  "occurrences": [
    { "symbol": "b21e…64 hex…", "role": "call", "range": [15, 9, 15, 13], "bytes": [511, 515], "enclosing": "3f9c…64 hex…" },
    { "symbol": null, "role": "reference", "range": [16, 2, 16, 3], "bytes": [520, 521], "enclosing": "3f9c…64 hex…", "note": "local binding" }
  ],
  "diagnostics": [
    { "range": [40, 1, 40, 20], "message": "undefined: Foo" }
  ]
}
```

- `symbols` lists every symbol the file declares, sorted by extent start: package-level types, functions, methods, variables, and constants, plus the fields and interface methods of the literal struct and interface types they declare. `key` is the v1 `IdentityKey()` the syntax extractor already produces, which maps an explorer tree node to its entry and is the only identity a `syntax` document has (`id` is null there). `name` is the identifier range shown in navigation; `extent` is the whole declaration including its doc comment. A proven type declaration in format v2 has `type_form` set to `struct`, `interface`, `other`, or `alias`; the validator checks that it agrees with the canonical shape. The query engine classifies immutable v1 type declarations from their stored shape and reports malformed shapes as errors. `implements` lists the non-empty, non-generic interface symbols declared in the package or its transitive imports that a declared non-interface, non-generic type satisfies by value or by pointer; restricting candidates to the import closure keeps the document a function of its input hash, which "all packages loaded in the run" would not. `shape`, `shape_hash`, `body_hash`, and `visibility` are the diff inputs; a `syntax` document renders `shape` from source text and omits `shape_hash`. In a `partial` document a declaration whose identity or shape involves an invalid type is not proven: it keeps its syntax facts (`key`, source-rendered `shape`, `body_hash`) with a null `id` and no `shape_hash`, `type_form`, or `implements`, or is omitted when the syntax extractor has no entry for it.
- `occurrences` lists every identifier use in the file, sorted by start byte. `role` is `definition`, `reference`, `call`, `write`, `type`, or `import`; an embedded field's name is both a `definition` of the field and a `type` use of the embedded type, and an import's occurrence spans its path literal and names the imported package's `package` symbol. `symbol` is null when the target is not a canonical symbol or could not be resolved; `note` then states why: `local binding` (parameters, results, receivers, and function-scoped declarations), `type parameter`, `label`, `member of a local or anonymous type`, `unresolved import`, `unproven: involves an invalid type`, or `unresolved` (the type checker recorded no object). In a `syntax` document every occurrence is a call with a null symbol and a `target` field holding the structured identifier the AST extractor records today. In a typed document a `call` occurrence carries the same call locator, spelled from the type checker: `target` names the callee's package, receiver type for a method, and name; `resolvable` is whether `symbol` is non-null; `local_root` whether `target.package` is the document's package; `statement_path` numbers the calls of the enclosing declaration in byte order; `text` is the callee expression as written; and `enclosing_key` is the enclosing declaration's `key`. A conversion `T(x)` is a `type` occurrence, not a call. `enclosing` is the innermost declared symbol containing the occurrence other than the one a `definition` occurrence defines, or null at file scope or when that declaration is unproven.
- `excluded`, present only on an `excluded` document, states why the file was not extracted: build constraints exclude the file, or no package builds from its directory, under the recorded `GOOS`, `GOARCH`, `CGO_ENABLED`, and tags. An excluded document has empty `symbols` and `occurrences`.
- `diagnostics` holds the package's load and type errors positioned in this file, with messages relative to the module root so that a document does not depend on the checkout's location. A `syntax` document produced because its package failed to load carries them too.
- Ranges are `[start_line, start_utf16_column, end_line, end_utf16_column]`, one-based; byte spans are `[start, end)`, zero-based. The publisher rejects any range whose end does not follow its start, and any two symbol extents that overlap other than by nesting.
- Explorer and `nodes` fields. Until typed documents replace them, each symbol entry also carries the per-declaration data the browse API and `nodes` queries read, so no second projection exists: `identifier` (the structured `uir.Identifier` whose `IdentityKey()` is `key`), `parent_key` (the parent declaration's key, absent for a top-level type), `child_slot` (`types`, `fields`, or `methods`), `ordinal` (the declaration's extraction order), `payload` (the UIR node JSON), `semantic_hash` (the node's `Hash()`), and, for struct fields, `field` (the field projection). A typed document takes these fields from the AST extraction of the same bytes, matched by name span. A declaration the AST extractor does not project (a variable, a constant, an interface method, or a field of a nested literal struct) carries an `identifier` built from its owner chain, so `key` still maps it, but no `child_slot`, `payload`, or `semantic_hash`; browse and `nodes` list only entries with a `child_slot`, and the call graph reads only occurrences that carry a call locator. A syntax occurrence also carries `enclosing_key` (the enclosing declaration's `key`, since `enclosing` is null), `resolvable` and `local_root` (whether the AST resolved the call's package and whether it names the file's own package), `statement_path` (`calls/NNNNNN` in call order within the enclosing function), and `text` (the callee expression as written). A syntax symbol's `shape` is the declaration's source text formatted without comments and body, and its `body_hash` digests the extent's `go/scanner` tokens without comments or line-end semicolons. `package_path` is the extractor's package, which carries a `_test` suffix for an external test package; `documents.package_path` is the source revision's package. The browse API and `nodes` matches report a declaration's `line` and `column` from the start of `name`, and `end_line` from the end of `extent`.

The posting table collapses document roles into three integer codes: 0 `definition` from `symbols`, 1 `reference` from every occurrence with a non-null symbol regardless of document role, and 2 `implements` from each `implements` entry (`storage.PostingRole`). A posting row names its document by ordinal and its symbol by handle; the primary key `(document_ordinal, symbol_handle, role)` serves the per-document probe and the document cascade, and `symbol_postings_symbol_idx (symbol_handle, role, root_ordinal, document_ordinal)` serves the per-symbol range, so a lookup filtered to one root never reads other roots' postings. Builtins receive no postings; their fan-in is useless for navigation and dominates row counts.

The publisher verifies before writing that every posting's symbol appears in the document, that every symbol a new document needs has a handle consistent with its module, package, visibility, and kind, that `symbol_count` and `occurrence_count` equal the document's array lengths, that every `symbol` and `enclosing` value is a known symbol id, that each entry's `visibility` and `kind` equal the `symbols` row, and that `package_path` equals the source revision's package path. Documents and postings are content-addressed, so a concurrent or repeated publication inserts them with `ON CONFLICT DO NOTHING` and re-reads, as `indexer/modules_sources.go` does for source revisions; postings for an existing document are skipped, not duplicated.

## Membership: which documents a snapshot activates

No delta or checkpoint table exists for documents. A snapshot's active documents are derived:

1. Effective sources for the snapshot give `(path_key, source_revision)` per path, from the source deltas.
2. `package_coverage` rows for the snapshot give `input_hash` per `package_path`.
3. For each path, the active document is the `documents` row with `(root_id, path_key, input_hash(package of that path))`, looked up in batches. `storage.ActiveDocuments` loads each row's `content` only when `ActiveDocumentOptions{Content: true}` asks for it; without it a reader gets each document's id, ordinal, coverage, and revision, finds the paths it needs, and loads just those with `storage.DocumentContents`.

Because the lookup is content-addressed, a snapshot that changed only dependencies reuses every document of every package whose input hash did not change, and a package whose input hash did change gets fresh documents for all of its files in one run. Browse, `nodes` queries, and typed queries all read the same documents.

Step 1 used to issue one query per base link. `storage.EffectiveSources` now issues one recursive CTE that walks the base chain and returns the first delta per path, tombstones included so Go can validate them, with a named recursion cap that turns a base cycle into an error. Both engines support `WITH RECURSIVE` and window functions; the core of the query is:

```sql
WITH RECURSIVE chain(id, base_id, depth) AS (
  SELECT id, base_snapshot_id, 0 FROM snapshots WHERE id = ?
  UNION ALL
  SELECT s.id, s.base_snapshot_id, c.depth + 1
  FROM snapshots s JOIN chain c ON s.id = c.base_id
),
ranked AS (
  SELECT d.path_key, d.revision_id, d.operation,
         ROW_NUMBER() OVER (PARTITION BY d.path_key ORDER BY c.depth) AS rank
  FROM source_deltas d JOIN chain c ON c.id = d.snapshot_id
)
SELECT path_key, revision_id FROM ranked WHERE rank = 1 AND operation = 'set';
```

Chain length is bounded only by history depth; the CTE makes that one query rather than one per link. If measured chain walks become the dominant cost, a source checkpoint table is the follow-up. It is not part of this design.

### Symbol membership: which symbols a snapshot defines

Unlike documents, symbol membership is stored as deltas. A snapshot's **defined-symbol set** is every declaration with a canonical id in its active documents; syntax declarations and the unproven declarations of a `partial` document have no id and no handle and are never in it. `symbol_deltas` records how that set differs from the base's: `set` with the symbol's fingerprints when it is new or its fingerprints changed, `delete` when the base defined it and the snapshot does not. A fingerprint is the first eight bytes of the `shape_hash` or `body_hash` read as a signed int64 (`storage.SymbolFingerprint`).

The publisher writes the deltas in the publication transaction from changed paths only. A path's active document is keyed by its package input hash, so it compares the base's and the new snapshot's keys and reads just the documents whose key differs: the base's stored documents for those paths, and the extraction for the new side. Unchanged documents are never read. Declarations are grouped by id across the changed documents; a symbol on both sides with equal fingerprints, such as one that moved between two changed files, gets no row. A snapshot without a base records every defined symbol as `set`, and a dependency bump that re-keys no document records nothing. This is sound because a canonical id includes its package, whose files share one directory and one input hash and are re-keyed together; the publisher fails if an id it reads is declared in two package directories. Every `func init` of a package shares one canonical id, so `storage.FoldDeclarations` combines several declarations of one id order-independently into one pair of fingerprints.

`storage.EffectiveSymbols` reads the set with the same base-chain walk as `EffectiveSources`, carrying each link's snapshot ordinal and joining `symbol_deltas` on it: the newest row per handle wins and tombstones drop out. `storage.DefinedSymbols` answers the question queries actually ask, "which of these handles does the snapshot define", with the same CTE restricted before ranking to an IN list of at most 256 handles, which every chain link probes on the `(snapshot_ordinal, symbol_handle)` primary key; its cost follows the handles asked about, not the size of the snapshot. Because a snapshot defines a symbol exactly when one of its active documents has a `definition` posting for it, both answer membership without reading documents or postings.

## Diffing two commits

A diff takes two git commits `A..B` and a root, and is computed from the two snapshots' active documents plus, for exact line counts, the two commits' blobs. No diff table is stored: both inputs are immutable, so a result is reproducible and may be cached by the caller.

**Commit to snapshot.** For each commit, select from the `(root_id, revision)` index the snapshots of the root whose `revision` equals the commit and whose `worktree_state` is `clean`; take the newest. If the only matches are `dirty`, the diff fails and names them, because their bytes may not be the commit's bytes; `--snapshot-from` and `--snapshot-to` override the selection explicitly. If a commit has no snapshot, the diff fails and states that the commit must be indexed first; indexing an arbitrary commit through a temporary worktree is a separate command and is out of scope here. Both snapshots must share `configuration_hash`, otherwise `shape_hash` and `body_hash` are not comparable and the diff fails saying so.

**Changed files.** Derive both active document maps without content: the membership needs only each path's document id, ordinal, and coverage. Paths with equal document ids on both sides are unchanged and are skipped without reading them. Paths present on one side only are added or removed files.

**Symbol diff (a).** Symbols are classified by identity across the whole diff, so a symbol that moved between files is still one symbol. For changed `indexed` documents the classification needs no document: read both snapshots' effective symbols, then the `definition` postings of each side's changed documents, which say which changed documents define each handle on each side and how many declarations they hold. The two must agree (a handle that a changed document defines is effective on exactly the sides whose changed documents define it, and a handle whose effective fingerprints differ between the sides must be declared by some changed document), otherwise the diff fails naming the handle. Each symbol declared once per side is classified:

| Class | Condition |
| --- | --- |
| `added` | defined only in B |
| `removed` | defined only in A |
| `signature` | defined on both sides, shape fingerprint differs |
| `body` | defined on both sides, shape fingerprint equal, body fingerprint differs |
| `moved` | defined on both sides, fingerprints equal, defining `path_key` differs |
| unchanged | defined on both sides, fingerprints and path equal; omitted |

A package with a `syntax` or `partial` changed document on either side (a keyed package), and a symbol declared more than once on a side (only the shared `func init` id), are instead matched over their decoded documents, first by id and then by `key`, and classified from the full hashes. Everywhere else a fingerprint stands for its hash, so two different shapes or bodies whose hashes share their first eight bytes would read as unchanged.

**Which documents are read.** Only those the output needs: with `--stat`, every changed document, for line counts; otherwise the documents of keyed packages, `excluded` documents, both sides of a symbol declared more than once, and, for a row the visibility filter shows, the new side of an `added` symbol, the old side of a `removed` one, and both sides of a `signature` change, whose shapes the row prints. A shown `body` or `moved` row prints no shape, so it is named from its `symbols` row and its owners' names (`storage.OwnedSymbols`, `storage.DeclarationIdentifier`) without decoding a document.

A rename appears as `removed` plus `added`, because identity includes the name; the output does not guess pairings. A parameter-type change likewise appears as `removed` plus `added` of the old and new identities, grouped under the old symbol's owner and name so the reader sees them together. The `--visibility` filter is `exported` by default and keeps a symbol when its `visibility` on either side matches; `internal` and `all` are the other values. The default output is therefore the interface change list: exported symbols added, removed, or changed in signature. Each row carries kind, owner, name, both `shape` strings when they differ, a shape diff for `signature` rows, and both file paths.

**Signature diff rendering.** A `signature` row shows what changed in the shape, not only that it changed. The two canonical `shape` renderings are line-diffed (Myers over lines). Unchanged lines print with a two-space prefix, removed lines with `-`, added lines with `+`. A removed line immediately followed by an added line is a replaced line, and the pair is additionally token-diffed with `go/scanner` tokens so the reader sees which parameter or type moved: removed tokens render red with strikethrough, added tokens green and bold, unchanged tokens plain. A one-line signature therefore prints as a single replaced pair with token marks, while a struct change prints as a field-level line diff. Rendering goes through clicky `api.Text`, whose builder already provides `Strikethrough()` and colour, so the terminal gets ANSI strikethrough, markdown gets `~~removed~~` and `**added**`, HTML gets `<del>` and `<ins>`, and JSON carries the structured form: `shape_diff` as a list of lines, each `{op: "equal"|"delete"|"insert", tokens: [{op, text}]}`. The same renderer serves the `removed`-plus-`added` grouping of a parameter-type change, diffing the old identity's shape against the new one so a type change reads as one signature edit. Package-level `export_shape_hash` equality is the fast pre-check: such a package contributes no exported `added`, `removed`, or `signature` rows and is skipped when the filter is `exported`. A `syntax` document on either side has no ids, so its symbols are matched by `key` and can only be classified `added`, `removed`, `body`, or `moved`; the row is marked `syntax`.

**Line attribution (b).** For each changed file, read both commits' bytes from Git (`git cat-file` on the blob at that commit in a registered checkout of the root) and verify each against the source revision's `content_hash`; a mismatch or a missing checkout fails the diff for that file with the reason, and the symbol diff for that file is still reported. Each side's document gives symbol extents in bytes. The file is partitioned into segments: one per outermost symbol extent, plus the gaps between them, which form a single `(file scope)` segment covering package clause, imports, comments, and anything not inside a declaration. Segments are paired by symbol id (or by `key` for `syntax` documents), and the gap segments are paired with each other. Each pair is line-diffed independently (Myers over lines), which yields `+added -removed` per symbol exactly, because a change inside one declaration cannot be attributed to another. A symbol present on one side only contributes all of its extent lines as added or removed. A `moved` symbol is diffed across files and reported under the destination file with the source path noted.

Per-file totals are the sums of their segment pairs, and per-package totals the sums of their files, so `store.go +14 -5` equals the sum of its symbol rows plus its file-scope row.

```text
example.org/service/invoices                          +14 -5
  invoices/store.go                                   +14 -5
    Store.Save          signature   +10 -3
      - func (s *Store) Save(ctx context.Context, inv Invoice) error
      + func (s *Store) Save(ctx context.Context, inv Invoice, opts ...SaveOption) (Receipt, error)
    Store.load          body        +4  -2
    (file scope)                    +0  -0
  invoices/model.go                                   +6  -6
    Invoice             signature   +1  -1
        type Invoice struct {
          ID       InvoiceID
      -   Total    int
      +   Total    Money
      +   Notes    string
        }
    Invoice.Total       added       +6  -0   func (i Invoice) Total() Money
    Invoice.total       removed     +0  -6   func (i Invoice) total() Money
```

In a terminal the `Store.Save` pair renders as one line with token marks rather than two full lines: the removed `) error` tail is red and struck through, and `, opts ...SaveOption) (Receipt, error)` is green and bold, so the reader sees the added variadic parameter and the new result tuple without comparing the lines by eye. In markdown the same pair is `func (s *Store) Save(ctx context.Context, inv Invoice~~) error~~**, opts ...SaveOption) (Receipt, error)**`. The plain-text form above is what `--format text` and non-TTY output print.

With `--visibility exported` the `Store.load` and `Invoice.total` rows are hidden; the file totals then state that hidden rows exist rather than silently summing to less than the file's diff.

**Coverage.** A `partial` file on either side still diffs the symbols it proved; the row is marked `partial` so a missing symbol is not read as removed. An `excluded` file is listed as excluded with its line diff attributed entirely to file scope.

**Cost.** Two content-free membership derivations, two effective-symbol walks, the definition postings of the changed documents, and batched content loads of the documents chosen above. Package-granular input hashes re-key sibling files even when only one file changed; their postings are read, but their symbols' fingerprints compare equal, so without `--stat` they are omitted without decoding a document. Git reads are bounded by changed files.

## Index inventory

All indexes are listed with their tables above. Named secondary indexes, in HCL naming: `locations_parent_idx`, `snapshots_location_started_idx`, `snapshots_base_idx`, `snapshots_root_revision_idx`, `source_deltas_revision_id_idx`, `symbols_lookup_idx`, `symbols_search_idx`, `documents_source_idx`, `symbol_postings_symbol_idx` over `(symbol_handle, role, root_ordinal, document_ordinal)`, `symbol_deltas_handle_idx` over `(symbol_handle, snapshot_ordinal)`, `package_coverage_input_idx`. Unique indexes are named `<table>_<columns>_key`; among them `symbols_handle_key` is the B-tree that handle ranges scan (selector candidates, and the largest handle of a bucket when a local is allocated), and `modules_ordinal_key`, `snapshots_ordinal_key`, and `documents_ordinal_key` are the targets of the posting and delta foreign keys. `symbols.owner_id` still has no index of its own: a lookup by owner alone scans `symbols`, and owner chains are loaded by id in batches instead.

`search_name` is the symbol's `name` lowercased and restricted to `[a-z0-9]`, with every other character (including `_`) removed; a name with none of those characters, such as `_`, stores an empty `search_name` and is found only by exact name. `storage.SearchName` is the one implementation, shared by the indexer and the query layer. A prefix search is then `search_name >= ? AND search_name < ?`, which uses the B-tree on both engines. The upper bound increments the prefix within the ordered alphabet `0-9` then `a-z` with carry (`9` becomes `a`; a trailing `z` is dropped and the character before it increments), and a prefix of only `z` has no upper bound. The bound never leaves the alphabet, because a punctuation byte sorts below digits and letters under glibc and ICU collations and would make the range empty. The query layer still keeps only the rows whose `search_name` starts with the prefix, so a collation that orders the range differently can only over-fetch. Because `search_name` and `visibility` are derived, publication upserts a symbol on conflict of `id` and refreshes both columns from the incoming row, so a reindex after a normalization change rewrites existing rows; `canonical_key` and the other identity facts are still verified against the stored row. Column collations and operator classes are outside the portable subset, so a general `LIKE 'prefix%'` must not be relied on. Qualified input such as `Store.Save` is split by the query layer: resolve owners by `search_name = 'store'`, then filter children by `owner_id`. Substring and fuzzy search need a separate design.

## Query and update examples

**References to B at every head.** Resolve B through `symbols_lookup_idx`; a selector matching several symbols returns candidates first. Map B's id to its handle once per query. For each selected location head, derive its active document ordinals. Then read `symbol_postings_symbol_idx` for `(handle(B), 1, root_ordinal)` and intersect with the active set; the query layer reads the root's posting range when it holds no more rows than the active set (bounded at one row past it), and otherwise probes the posting key with the active ordinals in batched `IN` lists. Load the matching documents, filter occurrences with `symbol = B`, and return one row per occurrence with path, range, role, and enclosing symbol, mapping handles back to ids. Declaration locations come from the same intersection with role 0 (`definition`); before reading those postings, `DefinedSymbols` tells which snapshots define B at all, and a root none of whose scopes does is skipped. A same-location declaration is preferred for display and other heads remain visible as candidates. Reference rows are never multiplied by the number of declaration locations.

**References in a historical snapshot.** Identical, with the active set derived for that snapshot. A `syntax` or `excluded` package in scope is reported as such so an empty result is not mistaken for proven absence.

**Callers of B, interface-aware.** Postings with role `implements` for interface I give the concrete types that satisfy I. Callers of a concrete method `T.M` are the references to `T.M` plus the references to `I.M` for every I that T implements, when the caller asks for dispatch-inclusive results. Dispatch through an interface declared outside the loaded packages is not proven.

**Callees of A.** Load A's defining document (the `definition` posting of `handle(A)` intersected with the active set) and return occurrences whose `enclosing` is A and whose role is `call`.

**Nodes and browse.** The existing `nodes where …` predicates and the explorer read `symbols` entries from active documents, typed or syntax, so the current AST-only behaviour is preserved for packages that do not type-check.

**Typed selectors.** A `pkg:` selector, or a symbol selector qualified by a package path, reads its candidates through the handle ranges of the registered packages it can match; any other selector reads each admitted root module's whole range. The ranges are merged and ORed into `handle BETWEEN` conditions over `symbols_handle_key`, and the candidates are then kept only where a selected snapshot of their own root defines them (`DefinedSymbols`).

**Name search and resolution.** Range-scan `symbols_search_idx` (spelling resolution and suggestions both take this path), keep symbols that a selected snapshot defines (`DefinedSymbols`, from symbol deltas) or that an active document references or implements (postings, read only for the symbols no snapshot defines), and rank by kind and module.

**Diff.** `uir diff <from>..<to> --root example.org/service` lists exported symbol changes; `--visibility all` includes internal symbols; `--stat` adds per-file and per-symbol line counts and requires readable Git blobs.

| Edit | Symbols | Documents, postings, and symbol deltas | Diff classification |
| --- | --- | --- | --- |
| Insert a comment above a use of B | Unchanged | Package input hash changes; every file in the package gets a new document with identical postings; no symbol delta, because `body_hash` ignores comments | `body` (layout only, with `--stat`) if inside a symbol's extent, otherwise file scope `+1 -0` |
| Add a second call from A to B | Unchanged | New documents for the package; posting `(doc, B, reference)` count becomes 2; `set` for A with a new body fingerprint | `body` on A |
| Change A's parameter name | Unchanged | New documents for the package; `set` for A with a new shape fingerprint | `signature` on A (names are in the shape, not the identity) |
| Change A's parameter type | New symbol for A; old retained | New documents for the package and, if A is exported, for every dependent package; `delete` for old A, `set` for new A | `removed` old A, `added` new A, grouped |
| Move B to another file in the same package | Unchanged | New documents; B's `definition` posting moves; no symbol delta, because B's fingerprints are equal | `moved` |
| Change an exported return or field type | Identity may remain | Export shape changes; every transitively dependent package is re-extracted; `set` for the changed symbol | `signature` |
| `go get` bumping a dependency | Unchanged | New snapshot with zero source deltas; only importing packages get new documents, and their symbols get deltas only if their fingerprints change | No symbol rows; `go.sum` is a changed file with file-scope lines |

**Cost note on package granularity.** Because a package's input hash covers all of its files, editing one file re-extracts and re-stores documents for every file in that package. That is the price of keeping the key content-addressed and the document membership derivation free of per-file delta rows. It does not inflate symbol deltas, which record only symbols whose fingerprints changed. If measurement shows this dominating, the refinement is a per-file input hash that combines the file's content hash with the package's export-and-imports hash rather than with sibling file hashes; it changes only the key definition, not the tables, and shrinks diff reads to exactly the changed files.

## Expected size and cost

Let `F` be files per module, `P` packages, `S` snapshots, `c` files re-extracted per snapshot, `k` distinct symbols mentioned per file, and `L` active location heads.

- Documents: one row per `(path, input_hash)`. History grows by `c` documents per snapshot, each a few kilobytes; this replaces the projection column rather than adding to it.
- Postings: `k` rows per document, typically 3 to 5 times fewer than occurrences in real files, each five integers (document ordinal, root ordinal, handle, role, count) plus two index entries.
- Package coverage: `P` rows per snapshot, `O(S × P)`.
- Symbols: one row per distinct identity ever observed, retained, each with its handle.
- Symbol registry: one `symbol_modules` row per module key and one `symbol_packages` row per package path ever observed.
- Symbol deltas: one row per symbol added, changed, or removed per snapshot, plus every defined symbol for a snapshot without a base.
- Membership: no document rows; one recursive CTE plus `P` package rows plus `F / 256` batched key lookups per snapshot derivation. Symbol membership is one recursive CTE over the deltas.
- Reference lookup: one derivation, one posting range scan bounded by `(handle, role, root ordinal)`, then document reads equal to the number of matching files. No `O(L × R)` posting tables exist.
- Diff: two content-free derivations, two symbol-delta walks, definition postings of changed documents, document reads only where the output needs shapes, keys, or line counts, Git reads for changed files, and in-memory line diffs per symbol pair.

Using the earlier illustration (100 modules, 500 files, 10,000 occurrences per module, 1,000 snapshots, one 20-occurrence file changing per snapshot, 5-file packages): about 550,000 documents, roughly 8 million posting rows at 15 distinct symbols per document, 5 million package coverage rows, and no occurrence, checkpoint, head, or diff rows. The occurrence-row design stored about 3 million occurrence rows plus 1 million head postings plus 800,000 checkpoint pointers under an assumption that ignored package re-typing. With realistic files of 200 to 500 occurrences and 60 to 100 distinct symbols the posting design stores four to five times fewer rows; with the toy 20-occurrence file it does not, and its saving is row width and the absence of position rows. These are algorithmic expectations, not measured latency guarantees; step 8 below measures them.

**Measured** (step 8, [benchmarks](benchmarks.md), SQLite and PostgreSQL 16 on this repository and `flanksource/commons`):

- Documents average 145 KB, which is 1.4 KB per declared symbol and 235 B per occurrence. That is far above the "few kilobytes" assumed above, and documents are 66 to 72 % of the database.
- A single-file body edit re-stores the whole package: 8 to 10 documents, 790 to 880 postings, and 1.4 to 1.7 MB on SQLite. After 200 such commits the commons database grew from 17.5 MB to 350 MB, with 1,708 documents and 182,568 postings.
- Postings cost about 490 B each in SQLite once both indexes are included. Under compact handles they cost 73 B on SQLite and 165 B on PostgreSQL (cold five-checkout corpus, [compact symbol handles](symbol-compact-ids.md)).
- The recursive CTE over a 200-link chain takes 1 ms. Posting lookups are covering range scans of `symbol_postings_symbol_idx` on both engines.
- Per head, the membership derivation's real cost is reading every active document's `content` (about 15 MB). That motivates a content-free membership lookup, not the phase-2 head table. `ActiveDocuments` now omits `content` unless asked; the diff uses that, while the query layer still loads content for every active document.
- Unchanged runs now skip type-checking: 3.3 to 4.5 s before, 0.14 to 0.67 s after. Other runs are dominated by the 4 to 15 s `go/packages` load.

Discovery still reads and hashes all included files on each run. Extraction runs through `go/packages` on changed packages and their dependents and completes before the publication transaction opens: the transaction allocates handles for new symbols and ordinals for new documents and the snapshot, writes symbols, documents, postings, package rows, the snapshot row, and its symbol deltas, then advances the head with the existing version check. SQLite's single connection is never held across type-checking.

## Phase-2 option: head materialization

If measured head queries across many locations are too slow because each head derivation repeats the CTE and key lookups, add `head_documents (location_id, root_id, path_key, document_id)` with PK `(location_id, path_key)`, replaced for changed paths in the publication transaction. It holds `O(L × F)` small rows, not `O(L × R)`, and reference queries join it directly with postings. The criterion for adding it is a benchmark on a real workspace showing derivation above a fixed budget per head; it is not part of the initial schema.
