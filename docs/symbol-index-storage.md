# Snapshot-aware symbol index: schema review

Document format 8 adds optional `declared_type` on proven package-level `var` declarations. Go indexing records the existing canonical type encoding, with full import paths and recursively resolved aliases, in immutable documents. This fact does not participate in global symbol identity or declaration fingerprints. `symbol.type` reads the selected snapshot's declaration; older/missing facts require reindexing or producer republishing. Type queries require complete typed coverage and never reconstruct types from source blobs. The JSON extension requires no new database table; document and indexer versions distinguish newly extracted facts.

**Status:** Implemented. The schema is created by migrations [`04_module_roots.hcl`](../storage/migrations/04_module_roots.hcl), [`05_source_deltas.hcl`](../storage/migrations/05_source_deltas.hcl), [`06_symbol_index.hcl`](../storage/migrations/06_symbol_index.hcl), and [`07_symbol_handles.hcl`](../storage/migrations/07_symbol_handles.hcl); this document is the design record of that change, which renamed and revised the seven `uir_`-prefixed tables and added four, and of the compact handles that followed it. The [ERD](uir-gorm-erd.tsx) shows the model.

**Compact handles (landed 2026-09-27).** The SHA-256 symbol id is still the identity everywhere outside the database: documents, canonical keys, export shape hashes, input hashes, and every API and JSON result. Inside it, each symbol also has a database-local 64-bit `handle` (H64b: `0 | module 11 | package 16 | visibility 1 | kind 6 | local 29`, numbered through the `symbol_modules`, `symbol_packages`, and `symbol_kinds` registries), and `modules`, `snapshots`, and `documents` have dense database-local `ordinal`s. Postings are keyed by document ordinal, symbol handle, and an integer role, and a new `symbol_deltas` table records per snapshot how its defined-symbol set changed, with layered (public, private, content) fingerprints. Queries answer "does this snapshot define it" from the deltas and read selector candidates through handle ranges; the diff classifies from the fingerprints and reads only the documents its output needs. A database of the previous generation keeps its registrations and loses its index on open, and `uir reindex` rebuilds it. The tables below describe the landed schema; the evaluation and measurements are in [compact symbol handles and symbol deltas](symbol-compact-ids.md), and the operational detail in the [storage design](../storage/README.md#compact-symbol-handles).

The query syntax in the original design record below has been superseded by the [compact query grammar](query.md).

## Goal and storage boundary

Store, for every indexed file version, one document holding the facts extracted from it: the symbols it declares with their signatures and hashes, the symbols it mentions, and where. When the package type-checks those facts are compiler-proven; otherwise the document holds the syntax-only projection the AST extractor produces today. A reference result must include the source filename and exact range from the selected snapshot. Resolving a symbol's declaration is a second lookup against files active in the selected branch or snapshot, so one symbol identity may have several declaration locations across checkout heads. A diff between two commits must list symbols added, removed, and changed, filtered by visibility, and attribute line additions and removals to file and symbol.

Source bytes remain in Git or the local checkout. The database retains hashes, symbol identities, one document per file version, an inverted index from symbol to the documents that mention it, and per-snapshot symbol deltas. Documents retain positions and full per-symbol public, private, and content hashes; symbol deltas keep a 64-bit fingerprint of each. Historical source viewing and line diffs require hash-verified bytes. Stored [file and callable metrics](sql-query.md#stored-metrics) remain queryable without those bytes: migration [`19_metrics.hcl`](../storage/migrations/19_metrics.hcl) adds immutable `source_metrics` by source revision and metric version, plus `declaration_metrics` by document ordinal and declaration key, projecting canonical handles, name positions, parameter counts, and optional body spans. Publication writes them atomically with their source revisions and documents; pruning cascades their deletion. Migration does not backfill metrics, so a query requesting unavailable metrics fails with reindex or republish guidance. Document format 10 adds `measures`, a producer's own integer metric values per declaration, which [`22_producer_metrics.hcl`](../storage/migrations/22_producer_metrics.hcl) stores in `declaration_measures` beside the kinds' declared metrics in `symbol_kind_metrics` ([producer metrics](sql-query.md#producer-metrics)).

The schema uses the repository's portable Atlas HCL subset: `uuid`, `text`, `integer`/`bigint`, `jsonb`, and `timestamptz`; column-based B-tree indexes; primary, unique, foreign-key, and check constraints. PostgreSQL uses those types directly. The SQLite adapter maps them to compatible types and keeps keys and indexes. No view, materialized view, trigger, GIN, trigram, expression index, sequence, or column collation is required, because none of those is portable.

In the tables below, every column is `NOT NULL` unless suffixed with `?`. `PK` and `UQ` each imply an index. All paths are module-relative slash-separated `path_key` values. All line and UTF-16 column numbers are one-based; byte offsets are zero-based, with an exclusive end offset. Every foreign key uses `ON UPDATE NO ACTION`; its `ON DELETE` action is shown with the reference, and unqualified `NO ACTION` means deletion is blocked while a referencing row remains.

### Snapshot trigger

Before this design, `indexer/discovery.go` hashed only `.go` files into `ContentSetHash`, and `indexer/modules.go` skipped snapshot creation when revision, content-set hash, configuration hash, and extractor version matched the base. Under that rule a `go get -u`, a `go.work` edit, or an exported-type change in a workspace sibling produces no snapshot and has nowhere to record new facts. Three changes to that seam are part of this design.

1. `ContentSetHash` also covers the dependency manifests: `go.mod` and `go.sum` under their module-relative paths, and the workspace's `go.work` and `go.work.sum` (found through `go env GOWORK`, which may sit above the module) under the fixed keys `go.work` and `go.work.sum`. A dependency bump then yields a snapshot with zero source deltas, which the storage layer already permits.
2. `ConfigurationHash` covers the indexer version and the build variant: `GOOS`, `GOARCH`, build tags, `CGO_ENABLED`, and the Go toolchain version. Exactly one variant is indexed per snapshot; a second variant is a configuration change and a new snapshot.
3. The unchanged check compares `revision`, `content_set_hash`, `configuration_hash`, and `context_hash` (defined below) with the base snapshot. The last catches a workspace sibling whose export shape changed while this module's bytes did not.

`worktree_state` is `clean` when `git status --porcelain` reports no changes under the module and every indexed file is tracked by Git (`git ls-files`), `dirty` otherwise, and `unknown` without Git, in which case `revision` is empty. Discovery excludes Git-ignored files, while the tracked-file check ensures that an untracked source is not recorded as `clean`. A commit-to-commit diff must know whether a snapshot's bytes are the commit's bytes.

## Hashes and identities

All digests are lowercase hexadecimal SHA-256 of a versioned, length-delimited canonical encoding.

**Symbol identity.** `symbols.id` digests `(identity_version, module_key, package_path, kind, owner_id, name, ordered parameter type identities)`. `canonical_key` stores that encoding and is unique, so an insert verifies that an existing digest has exactly the expected value. Parameter names, return types, field types, source path, line, and bodies do not enter identity. `module_key` is the Go module path (`root_key` for indexed roots), `std` for the standard library, and empty only for `kind = 'builtin'`. Parameter types use fully qualified named types and recursively encoded composite types; type parameters are encoded by ordinal. Local bindings, parameters, and labels are not canonical symbols: their occurrences stay inside the document with a null symbol, because they are never referenced across files. Canonical identities exist only for typed documents; a `syntax` document's symbol entries carry the v1 `IdentityKey()` and a null id, because unresolved parameter types cannot produce a trustworthy identity.

**Visibility.** A symbol is `exported` when its name is exported and every owner in its chain is exported; otherwise it is `internal`. A method on an unexported type is therefore `internal` even though its name is capitalised.

**Symbol layers.** Every proven symbol carries three Merkle-nested hashes, the same layers `uir.Fingerprint` defines for UIR nodes:

| Layer | Hash | What it digests |
| --- | --- | --- |
| public | `public_hash` | `public_shape`: what a consumer outside the symbol's package observes. A struct's exported fields (an embedded exported type counts) with their tags, an interface's exported methods and type-set terms, each followed by an `opaque` line when unexported members exist, since those still decide comparability and whether an unkeyed literal compiles. For functions, methods, variables, constants, aliases, and other named types the public shape is the whole declaration. |
| private | `private_hash` | `public_hash` and `shape`, the full declared structure: the complete signature including parameter names, results, and variadic-ness; every field with its name, type, tag, and embedding; the method set; the underlying type; the type and, for constants, the value. Because it digests `public_hash`, a public change is always a private change. |
| content | `content_hash` | The token stream of the declaration's extent with comments, whitespace, and layout tokens removed, and every name the declaration binds renamed to its position: the implementation. Layout tokens are statement separators before a closing `)` or `}`, another separator, or the end; trailing commas before `)` or `}`; and the `var`, `const`, or `type` keyword of an ungrouped declaration, so moving it into a group changes nothing. The renamed names are the receiver, parameters, results, type parameters, and local variables, constants, and types; a selector, a label, a field or method name, and an identifier key of a composite literal keep their spelling. A renamed parameter therefore changes `public_hash` and `private_hash` but not `content_hash`. |

Equal identity and equal `public_hash` mean the same interface to code outside the package; a differing `private_hash` with an equal `public_hash` is a structure-only change (adding an unexported field to an exported struct that already had one), and a differing `content_hash` with equal shape hashes is an implementation-only change. `shape` and `public_shape` are rendered in a canonical layout chosen so that two shapes diff line by line: a function or method signature is one line; a struct renders one field per line and an interface one method per line, each line `gofmt`-aligned, between a `type Name struct {` or `interface {` line and a closing `}`; a variable or constant is one line with its type and, for constants, its value. Each shape hash digests its rendering, so a shape diff never differs from a hash change. An unexported symbol's public shape follows the same rules.

**Export shape.** `export_shape_hash(P)` (`uir-export-shape-v4`) digests the sorted `(symbol id, API shape)` pairs of P's exported symbols, a `(type id, promoted selectors)` pair for every exported defined type that promotes exported methods or fields through an embedded field (exported or not, from P or another package), and the `export_shape_hash` of only the packages whose named types P's exported API reaches (`indexer.apiReferences`: exported signatures, fields, embedded fields of any visibility, constraints, and P's own unexported types an exported signature names), so adding an unexported field to an exported type re-extracts nothing outside P, and a change in a package P imports but does not name in its API re-extracts nothing outside P either. The API shape is the public layer encoded without names an importer cannot depend on: types are qualified by import path, and receiver, parameter, result, and type parameter names are left out (type parameter constraints, variadic-ness, field names, tags, embedding, the `opaque` marker, and constant values stay). `public_hash` keeps those names, because the diff reports them as signature changes, so a parameter rename changes `public_hash` but no importer's input, and retargeting an import from `foo/v1` to `bar/v1` changes the export shape even where `v1.Client` reads the same. Because it recurses through the packages an API references, a public change in an exported type that an API names, directly or through another API, changes every such dependent's shape; a change behind a private import does not. That is sound only because a document holds no closure facts: `implements`, which once listed interfaces from the whole import closure, is a snapshot-level fact (below). A known gap the transitive shape shared: a method of an unexported type of another package that an exported API names only through inference (`var V = dep.New()` returning `dep.impl`) is in no export shape. For a package outside the indexed roots it is `H(module path, module version, toolchain version)`; for the standard library it is `H("std", toolchain version)`. Neither requires type-checking the dependency. A workspace package that did not reach `indexed` coverage has no proven shape and therefore no `export_shape_hash`; as an import it contributes a stand-in digest of its file hashes and its own imports' shapes, so its importers still re-extract when it changes, and an import that no module provides contributes its import path. The module's own packages must still be type-checked to compute `context_hash`, so the unchanged decision is cheap only for dependencies; skipping the type-check when the content set, manifests and sibling shapes are all unchanged is a benchmark-step optimization.

**Package input hash.** `input_hash(P)` digests `(configuration_hash, package_path, sorted (path_key, content_hash) of P's files, sorted (import path, export_shape_hash) of P's direct imports)`. Two files of one package share it. It is the complete input to extracting P: same input hash, same documents. The converse does not hold: a changed input hash often renders byte-identical documents, which is why documents are not keyed by it.

**Snapshot context hash.** `context_hash(S)` digests `(configuration_hash, sorted (package_path, input_hash) of every package in the module)`.

**Document key.** A document is identified by `(root_id, path_key, content_digest)`. `content_digest` (`storage.DocumentDigest`, `uir-document-digest-v1`) is the SHA-256 of a length-delimited encoding of the document's source revision id, package path, indexer version, coverage, and canonical content (decoded and re-encoded with sorted keys and numbers as written, so the digest of rendered bytes equals the digest of what PostgreSQL's `jsonb` returns). The same bytes extracted under a changed dependency that render the same document keep it, with its ordinal and postings; a different rendering is a new document, and the old one remains valid for older snapshots. `documents.input_hash` stays as provenance, the package input hash the document was first rendered under; nothing selects by it.

`symbols` is global and is never cascaded. A symbol with no posting and no symbol delta is unreachable; a future garbage collector deletes such rows with `NOT EXISTS` over the posting and delta indexes, which both lead with the handle. No other retention is proposed, matching the existing policy that snapshots and source revisions are retained.

**Handles.** `symbols.handle` is a non-negative `bigint` laid out most significant bit first as `0 | module 11 | package 16 | visibility 1 | kind 6 | local 29` (H64b, `storage/symbolhandle`). The module and package numbers come from `symbol_modules`, which reserves 0 for builtins (`''`) and 1 for `std` because neither has a `modules` row, and `symbol_packages`, which numbers each module's package paths from 0. The kind code comes from `symbol_kinds`: 0 is reserved, the 18 builtin kinds hold 1–18, and a database's custom kinds (`oipa.rule`) are allocated from 63 downward; `symbols.kind` references the registry by name. `symbol_layout` records the layout, and a database without it (H64a, `kind 3 | local 32`) has its index discarded on open. The local is one past the largest stored handle of its (module, package, visibility, kind) bucket. Handles therefore sort by module, package, visibility, and kind, so "every symbol of a package", "every exported symbol of a package", and "every exported func of a package" are each one inclusive B-tree range. A handle depends on the order symbols were first published, so it is local to one database: it never enters a document, a hash, a canonical key, or a query result. Visibility is part of the handle, so a symbol whose derived visibility changes cannot be re-published under its old handle and fails loudly; a reindex into a fresh database is then required.

**Ordinals.** `modules.ordinal`, `snapshots.ordinal`, and `documents.ordinal` are dense database-local numbers from 1, allocated as one past the current maximum inside the publication transaction; a PostgreSQL publisher that loses an allocation race retries the whole publication, at most three times. Postings and symbol deltas carry the root's ordinal as a plain column rather than through a composite key with the document or snapshot, so the publisher takes it from the row it just wrote.

Coverage has one vocabulary at every level. `indexed`: type-checked without diagnostics. `partial`: type-checked with diagnostics; only proven facts are recorded. `syntax`: the package did not type-check, so the document holds the AST extractor's declarations and unresolved calls, and has no postings. `excluded`: not extracted (build constraints, `testdata`, generated exclusions); the document is empty and says why. A snapshot's `coverage` is the weakest of `indexed`, `partial` and `syntax` among its packages; `excluded` packages do not count unless every package is excluded, and a module with no packages is `indexed`.

### The document

`documents.content` is one JSON object. Its shape is versioned by `indexer_version`, so a format change is a new indexer version and new documents; documents are never migrated in place.

```json
{
  "version": 6,
  "package_path": "example.org/service/invoices",
  "symbols": [
    {
      "id": "3f9c…64 hex…",
      "key": "v1:[\"method\",\"\",\"example.org/service/invoices\",\"Store\",\"Save\",\"\",\"(context.Context,Invoice)->error\"]",
      "kind": "method",
      "visibility": "exported",
      "shape": "func (s *Store) Save(ctx context.Context, inv Invoice) error",
      "public_shape": "func (s *Store) Save(ctx context.Context, inv Invoice) error",
      "public_hash": "9d2a…64 hex…",
      "private_hash": "51b7…64 hex…",
      "content_hash": "c4e1…64 hex…",
      "name": [12, 17, 12, 21],
      "name_bytes": [418, 422],
      "extent": [12, 1, 30, 2],
      "extent_bytes": [406, 902]
    }
  ],
  "occurrences": [
    { "symbol": "b21e…64 hex…", "role": "call", "range": [15, 9, 15, 13], "bytes": [511, 515], "enclosing": "3f9c…64 hex…" },
    { "symbol": null, "role": "reference", "range": [16, 2, 16, 3], "bytes": [520, 521], "enclosing": "3f9c…64 hex…", "note": "local binding" }
  ],
  "diagnostics": [
    { "range": [40, 1, 40, 20], "message": "undefined: Foo" }
  ]
}
```

- `symbols` lists every symbol the file declares, sorted by extent start: package-level types, functions, methods, variables, and constants, plus the fields and interface methods of the literal struct and interface types they declare. `key` is the v1 `IdentityKey()` the syntax extractor already produces, which maps an explorer tree node to its entry and is the only identity a `syntax` document has (`id` is null there). `name` is the identifier range shown in navigation; `extent` is the whole declaration including its doc comment. A proven type declaration in format v2 has `type_form` set to `struct`, `interface`, `other`, or `alias`; the validator checks that it agrees with the canonical shape. The query engine classifies immutable v1 type declarations from their stored shape and reports malformed shapes as errors. Format 6 moved `implements` out of documents into [snapshot implements facts](#implements-facts); a format 2–5 document may still carry it, and nothing reads it. `embeds` stays: it names the types the declaration's own embedded fields spell, by identity, which depends only on the declaration and its direct imports. `shape`, `public_shape`, `public_hash`, `private_hash`, `content_hash`, and `visibility` are the diff inputs; every symbol has `shape` and `content_hash`, and a symbol with an `id` also has `public_shape`, `public_hash`, and `private_hash`. A `syntax` document renders `shape` from source text and omits `public_shape`, `public_hash`, and `private_hash`. In a `partial` document a declaration whose identity or shape involves an invalid type is not proven: it keeps its syntax facts (`key`, source-rendered `shape`, `content_hash`) with a null `id` and no `public_shape`, `public_hash`, `private_hash`, `type_form`, or `embeds`, or is omitted when the syntax extractor has no entry for it. Format 5 replaced format 4's `shape_hash` and `body_hash` with the three layers; a database holding format 4 documents is discarded on open (see [the cutover](#layered-fingerprint-cutover)).
- `occurrences` lists every identifier use in the file, sorted by start byte. `role` is `definition`, `reference`, `call`, `write`, `type`, or `import`; an embedded field's name is both a `definition` of the field and a `type` use of the embedded type, and an import's occurrence spans its path literal and names the imported package's `package` symbol. `symbol` is null when the target is not a canonical symbol or could not be resolved; `note` then states why: `local binding` (parameters, results, receivers, and function-scoped declarations), `type parameter`, `label`, `member of a local or anonymous type`, `unresolved import`, `unproven: involves an invalid type`, or `unresolved` (the type checker recorded no object). In a `syntax` document every occurrence is a call with a null symbol and a `target` field holding the structured identifier the AST extractor records today. In a typed document a `call` occurrence carries the same call locator, spelled from the type checker: `target` names the callee's package, receiver type for a method, and name; `resolvable` is whether `symbol` is non-null; `local_root` whether `target.package` is the document's package; `statement_path` numbers the calls of the enclosing declaration in byte order; `text` is the callee expression as written; and `enclosing_key` is the enclosing declaration's `key`. A conversion `T(x)` is a `type` occurrence, not a call. `enclosing` is the innermost declared symbol containing the occurrence other than the one a `definition` occurrence defines, or null at file scope or when that declaration is unproven.
- `excluded`, present only on an `excluded` document, states why the file was not extracted: build constraints exclude the file, or no package builds from its directory, under the recorded `GOOS`, `GOARCH`, `CGO_ENABLED`, and tags. An excluded document has empty `symbols` and `occurrences`.
- `diagnostics` holds the package's load and type errors positioned in this file, with messages relative to the module root so that a document does not depend on the checkout's location. A `syntax` document produced because its package failed to load carries them too.
- Ranges are `[start_line, start_utf16_column, end_line, end_utf16_column]`, one-based; byte spans are `[start, end)`, zero-based. The publisher rejects any range whose end does not follow its start, and any two symbol extents that overlap other than by nesting.
- Explorer and `nodes` fields. Until typed documents replace them, each symbol entry also carries the per-declaration data the browse API and `nodes` queries read, so no second projection exists: `identifier` (the structured `uir.Identifier` whose `IdentityKey()` is `key`), `parent_key` (the parent declaration's key, absent for a top-level type), `child_slot` (`types`, `fields`, or `methods`), `ordinal` (the declaration's extraction order), `payload` (the UIR node JSON), `semantic_hash` (the node's `Hash()`), and, for struct fields, `field` (the field projection). A typed document takes these fields from the AST extraction of the same bytes, matched by name span. A declaration the AST extractor does not project (a variable, a constant, an interface method, or a field of a nested literal struct) carries an `identifier` built from its owner chain, so `key` still maps it, but no `child_slot`, `payload`, or `semantic_hash`; browse and `nodes` list only entries with a `child_slot`, and the call graph reads only occurrences that carry a call locator. A syntax occurrence also carries `enclosing_key` (the enclosing declaration's `key`, since `enclosing` is null), `resolvable` and `local_root` (whether the AST resolved the call's package and whether it names the file's own package), `statement_path` (`calls/NNNNNN` in call order within the enclosing function), and `text` (the callee expression as written). A syntax symbol's `shape` is the declaration's source text formatted without comments and body, and its `content_hash` digests the extent's `go/scanner` tokens normalized as the content layer describes, resolving the names a declaration binds by block scoping over the syntax tree; a typed document resolves them from the type checker and leaves the same composite literal keys alone, so both give one declaration the same `content_hash`. `package_path` is the extractor's package, which carries a `_test` suffix for an external test package; `documents.package_path` is the source revision's package. The browse API and `nodes` matches report a declaration's `line` and `column` from the start of `name`, and `end_line` from the end of `extent`.

The posting table collapses document roles into integer codes: 0 `definition` from `symbols`, 1 `reference` from every occurrence with a non-null symbol regardless of document role, and 3 `embeds` from each `embeds` entry (`storage.PostingRole`); code 2 `implements` exists only in the postings of format 2–5 documents. A posting row names its document by ordinal and its symbol by handle; the primary key `(document_ordinal, symbol_handle, role)` serves the per-document probe and the document cascade, and `symbol_postings_symbol_idx (symbol_handle, role, root_ordinal, document_ordinal)` serves the per-symbol range, so a lookup filtered to one root never reads other roots' postings. Builtins receive no postings; their fan-in is useless for navigation and dominates row counts.

The publisher verifies before writing that every posting's symbol appears in the document, that every symbol a new document needs has a handle consistent with its module, package, visibility, and kind, that `symbol_count` and `occurrence_count` equal the document's array lengths, that every `symbol` and `enclosing` value is a known symbol id, that each entry's `visibility` and `kind` equal the `symbols` row, and that `package_path` equals the source revision's package path. Documents and postings are content-addressed, so a concurrent or repeated publication inserts them with `ON CONFLICT DO NOTHING` and re-reads, as `indexer/modules_sources.go` does for source revisions; postings for an existing document are skipped, not duplicated.

## Membership: which documents a snapshot activates

Document membership is stored as deltas, beside source and symbol deltas. `document_deltas` records how a snapshot's path → document binding differs from its base's: `set` binds a path to an immutable document by ordinal, `delete` drops a path the base served; a snapshot without a base holds a `set` for every path. `storage.ActiveDocuments` resolves it:

1. Effective sources for the snapshot give `(path_key, source_revision)` per path, from the source deltas.
2. `storage.EffectiveDocumentOrdinals` walks the same base chain and takes the newest document delta per path, tombstones dropping their path.
3. The bound documents are loaded by ordinal in batches. Every effective path must be bound, every bound document must belong to the snapshot's root and the path and describe the path's effective revision, and the snapshot's `package_coverage` rows must account for exactly its packages and their file counts; any gap is an error. `content` is loaded only when `ActiveDocumentOptions{Content: true}` asks for it; without it a reader gets each document's id, ordinal, digest, coverage, and revision, finds the paths it needs, and loads just those with `storage.DocumentContents`.

The foreign keys make a mis-binding unrepresentable: a delta's root must be its snapshot's (`(root_id, snapshot_ordinal)`), and its document must be of that root and path (`(root_id, path_key, document_ordinal)`).

**Publication.** The publisher renders every file of a package whose input hash differs from the base's, digests each rendered document, and binds the path to the document stored under `(root, path, digest)`: the base's bound document when its digest matches, otherwise a paired-key lookup (`(path_key, content_digest) IN (…)` within the root, at most 256 pairs per batch). Only a digest no document holds is inserted, with its postings. It then writes a `set` delta for each path whose bound document differs from the base's and a `delete` for each path the base served and the snapshot does not. A package whose input hash equals the base's keeps the base's bindings without rendering (`basePackages` reads its input hash from the base's `package_coverage`). Package coverage stays the package-analysis record (input hash, export shape, coverage, diagnostics); it no longer selects documents. Under `--force` every document is rendered and verified instead: a stored document under the same digest must equal the rendering (`sameJSON`), and a file whose package has the base's input hash must render the base's digest, or the publication fails with "changed without an indexer version change".

**Per-file failures.** A failure confined to one file never fails the module. A file whose document cannot be rendered, or whose rendered document fails a check its writes repeat (storage validation, or two symbols sharing the key its `declaration_metrics` rows are keyed by), is published, before anything is written, with its syntax extraction instead, else an empty document. Its package's coverage drops to `partial`, and its `package_coverage.diagnostics` gain `{path, rule: "uir/index", message}`; the snapshot's diagnostics summarize the same list, which `ModuleResult.Warnings` and `uir lint` report in lint's shape. A file that does not parse drops its whole package to `syntax` coverage, since its declarations are missing from type checking: the package's other files keep their syntax documents, the parse errors are `uir/coverage` diagnostics, and the file itself is published as an empty document with a `uir/index` warning. A package whose own load is clean but whose exported API names a type an erroring import left invalid gets the unproven export shape (its files' bytes) rather than failing. Database, transaction and input-change failures, and invariants across documents, still fail the module.

So a snapshot that changed only a dependency's API keeps every document of an importer whose rendering did not change, and an edit to one file of a package inserts one document and writes one delta. Browse, `nodes` queries, and typed queries all read the same documents.

### Document membership cutover

A database published before document deltas selected documents by package input hash. Opening it read-write (`storage.UirDB`) drops the `(root_id, path_key, input_hash)` key (on SQLite before migration, which refuses to drop an index; PostgreSQL's migration drops it), migrates, and completes the cutover in bounded, resumable transactions recorded in `document_membership`: every document gets its digest in batches of 64 in ordinal order, then every snapshot in ordinal order gets the deltas of the membership its package input hashes selected, a full set for a snapshot without a base and only the differences from its base's otherwise. Before the cutover, an unchanged file of a re-keyed package got a new, byte-identical document; the earliest such document of a path keeps the digest and the rest keep a null `content_digest`, still bound by ordinal by every snapshot that bound them, so document ids, ordinals, payloads, and postings are preserved and every snapshot's `ActiveDocuments` is unchanged. A new publication binds the earliest one by digest. `storage.OpenReadOnly` refuses a database whose cutover is missing or incomplete (`storage.ErrDocumentMembershipCutover`).

Step 1 used to issue one query per base link. `storage.EffectiveSources` now issues one recursive CTE that walks the base chain and returns the first delta per path, tombstones included so Go can validate them, with a named recursion cap that turns a base cycle into an error. Both engines support `WITH RECURSIVE` and window functions; the core of the query is:

```sql
WITH RECURSIVE chain(id, base_id, depth) AS (
  SELECT id, base_snapshot_id, 0 FROM snapshots WHERE id = ?
  UNION ALL
  SELECT s.id, s.base_snapshot_id, c.depth + 1
  FROM snapshots s JOIN chain c ON s.id = c.base_id
),
ranked AS (
  SELECT d.path_key, d.revision_id, d.operation,
         ROW_NUMBER() OVER (PARTITION BY d.path_key ORDER BY c.depth) AS rank
  FROM source_deltas d JOIN chain c ON c.id = d.snapshot_id
)
SELECT path_key, revision_id FROM ranked WHERE rank = 1 AND operation = 'set';
```

Chain length is bounded only by history depth; the CTE makes that one query rather than one per link. If measured chain walks become the dominant cost, a source checkpoint table is the follow-up. It is not part of this design.

### Symbol membership: which symbols a snapshot defines

Unlike documents, symbol membership is stored as deltas. A snapshot's **defined-symbol set** is every declaration with a canonical id in its active documents; syntax declarations and the unproven declarations of a `partial` document have no id and no handle and are never in it. `symbol_deltas` records how that set differs from the base's: `set` with the symbol's fingerprints when it is new or its fingerprints changed, `delete` when the base defined it and the snapshot does not. A `set` carries one fingerprint per layer, `public_fp`, `private_fp`, and `content_fp`: each the first eight bytes of the declaration's `public_hash`, `private_hash`, or `content_hash` read as a signed int64 (`storage.SymbolFingerprint`, `DocumentSymbol.Fingerprints`).

#### Layered fingerprint cutover

`symbol_deltas` once stored two fingerprints, `shape_fp` and `body_fp`, and documents (format 4) carried `shape_hash` and `body_hash`. Neither can be converted into the three layers without re-extracting, so `storage.UirDB` treats such a database as another stale generation, exactly as it does a pre-handle or H64a one (`storage/handle_cutover.go`): the catalog query that classifies the database also reports whether `symbol_deltas` has a `shape_fp` column, and when the recorded layout is current but the column is there, the database is the two-layer fingerprint generation. Before migration, in one transaction, the cutover drops the same index tables (`symbol_deltas`, `symbol_postings`, `snapshot_dependencies`, `package_coverage`, `documents`, `symbols`, `symbol_packages`, `symbol_modules`, `source_deltas`, `source_revisions`, `location_heads`, `snapshots`, `source_blobs`); `modules` with their ordinals, `locations`, `primary_locations`, `task_runs`, and `symbol_kinds` keep their rows. Migration then creates `symbol_deltas` as [13_layered_fingerprints.hcl](../storage/migrations/13_layered_fingerprints.hcl) declares it, and `UirDB` logs a warning to run `uir reindex`. `OpenReadOnly` refuses such a database with "database predates layered symbol fingerprints; open it read-write once or run uir reindex".

The publisher writes the deltas in the publication transaction from changed packages only: a package is changed when one of its paths is bound to a different document than in the base, or added or removed. It compares a changed package whole, the base's stored documents of all its paths and the extraction's of all its files, because one id may be declared in several files of a package and its fingerprints fold across all of them; documents of every other package are never read. Declarations are grouped by id across the changed packages; a symbol on both sides with equal fingerprints, such as one that moved between two files, gets no row. A snapshot without a base records every defined symbol as `set`, and a dependency bump that rebinds no document records nothing. This is sound because a canonical id includes its package, whose files share one directory; the publisher fails if an id it reads is declared in two package directories. Go never declares one id twice, since each `func init` carries its own discriminator ([canonical symbols](symbols.md#canonical-symbols)), but a producer may declare one id in several files, so `storage.FoldDeclarations` combines several declarations of one id order-independently into one triple of fingerprints, folding each layer apart.

`storage.EffectiveSymbols` reads the set with the same base-chain walk as `EffectiveSources`, carrying each link's snapshot ordinal and joining `symbol_deltas` on it: the newest row per handle wins and tombstones drop out. `storage.DefinedSymbols` answers the question queries actually ask, "which of these handles does the snapshot define", with the same CTE restricted before ranking to an IN list of at most 256 handles, which every chain link probes on the `(snapshot_ordinal, symbol_handle)` primary key; its cost follows the handles asked about, not the size of the snapshot. Because a snapshot defines a symbol exactly when one of its active documents has a `definition` posting for it, both answer membership without reading documents or postings.

### Implements facts

Which interfaces a type satisfies depends on every candidate interface, not on the type's file and its imports' APIs, so it is a snapshot-level fact rather than a document field ([17_implements.hcl](../storage/migrations/17_implements.hcl)). After a Go root's documents are extracted, `indexer.snapshotImplements` relates every non-interface, non-generic defined type the root's indexed or partial packages declare (proven declarations only) to each candidate interface it satisfies by value or by pointer, reused packages included. Candidates are the non-empty, non-generic, method-set package-level interfaces of the packages the root's variants reach through imports, without passing through another module's workspace package, admitted by what keys them: the root's own packages, any interface (their sources are the content set); standard-library and module-cache packages, exported interfaces (the toolchain and module versions key them); and another module's workspace package whose export shape a package input hash folds in, exported interfaces with only exported methods (that shape is all the context covers of it). The facts are therefore a function of what `context_hash` and the content set cover, and a type is related to an interface declared in a package it does not import. A method-name index tests a candidate only when the type's method set has every one of its method names.

| Table | Columns | Keys | References and checks |
| --- | --- | --- | --- |
| `implements_deltas` | `snapshot_ordinal bigint`, `root_ordinal integer`, `type_handle bigint`, `interface_handle bigint`, `operation text` | PK `(snapshot_ordinal,type_handle,interface_handle)`; index `(interface_handle,snapshot_ordinal)`; index `(type_handle,snapshot_ordinal)` | `snapshot_ordinal → snapshots.ordinal` CASCADE; `root_ordinal → modules.ordinal` CASCADE; `type_handle`, `interface_handle → symbols.handle` NO ACTION; `operation IN ('set','delete')` |
| `implements_facts` | `snapshot_ordinal bigint`, `root_ordinal integer`, `pair_count bigint` | PK `snapshot_ordinal` | `snapshot_ordinal → snapshots.ordinal` CASCADE; `root_ordinal → modules.ordinal` CASCADE; `pair_count >= 0` |

Publication compares the extraction's facts with the base's effective facts and writes a `set` for each new pair and a `delete` for each pair only the base holds, then the `implements_facts` row with the snapshot's pair count. A base published before snapshot-level facts has no row and contributes none. `storage.EffectiveImplements` resolves the facts along the base chain like `EffectiveSymbols`, the newest row per pair winning, restricted before ranking to IN lists of at most 256 type or interface handles; an unrestricted read checks the resolved count against `pair_count`. A snapshot without an `implements_facts` row is `storage.ErrNoImplementsFacts`, and the query layer asks for a reindex instead of reading old documents' `implements` entries. Pruning rebases a survivor's facts into `set` rows with its sources and symbols, and counts both handle columns as references when it looks for orphan symbols.

## Diffing two commits

A diff takes two git commits `A..B` and a root, and is computed from the two snapshots' active documents plus, for exact line counts, the two commits' blobs. No diff table is stored: both inputs are immutable, so a result is reproducible and may be cached by the caller.

**Commit to snapshot.** For each commit, select from the `(root_id, revision)` index the snapshots of the root whose `revision` equals the commit and whose `worktree_state` is `clean`; take the newest. If the only matches are `dirty`, the diff fails and names them, because their bytes may not be the commit's bytes; `--snapshot-from` and `--snapshot-to` override the selection explicitly. If a commit has no snapshot, the diff fails and states that the commit must be indexed first; indexing an arbitrary commit through a temporary worktree is a separate command and is out of scope here. Both snapshots must share `configuration_hash`, otherwise the layer hashes are not comparable and the diff fails saying so.

**Changed files.** Derive both active document maps without content: the membership needs only each path's document id, ordinal, and coverage. Paths with equal document ids on both sides are unchanged and are skipped without reading them. Paths present on one side only are added or removed files.

**Symbol diff (a).** Symbols are classified by identity across the whole diff, so a symbol that moved between files is still one symbol. For changed `indexed` documents the classification needs no document: read both snapshots' effective symbols, then the `definition` postings of each side's changed documents, which say which changed documents define each handle on each side and how many declarations they hold. The two must agree (a handle that a changed document defines is effective on exactly the sides whose changed documents define it, and a handle whose effective fingerprints differ between the sides must be declared by some changed document), otherwise the diff fails naming the handle. Each symbol declared once per side is classified:

| Class | Condition |
| --- | --- |
| `added` | defined only in B |
| `removed` | defined only in A |
| `signature` | defined on both sides, public fingerprint differs |
| `structure` | defined on both sides, public fingerprint equal, private fingerprint differs |
| `body` | defined on both sides, public and private fingerprints equal, content fingerprint differs |
| `moved` | defined on both sides, fingerprints equal, defining `path_key` differs |
| unchanged | defined on both sides, fingerprints and path equal; omitted |

A package with a `syntax` or `partial` changed document on either side (a keyed package), and a symbol declared more than once on a side, are instead matched over their decoded documents, first by id and then by `key`, and classified from the full hashes. Everywhere else a fingerprint stands for its hash, so two different shapes or bodies whose hashes share their first eight bytes would read as unchanged.

**Which documents are read.** Only those the output needs: with `--stat`, every changed document, for line counts; otherwise the documents of keyed packages, `excluded` documents, both sides of a symbol declared more than once, and, for a row the visibility filter shows, the new side of an `added` symbol, the old side of a `removed` one, and both sides of a `signature` or `structure` change, whose shapes the row prints. A shown `body` or `moved` row prints no shape, so it is named from its `symbols` row and its owners' names (`storage.OwnedSymbols`, `storage.DeclarationIdentifier`) without decoding a document.

A rename appears as `removed` plus `added`, because identity includes the name; the output does not guess pairings. A parameter-type change likewise appears as `removed` plus `added` of the old and new identities, grouped under the old symbol's owner and name so the reader sees them together. The `--visibility` filter is `exported` by default and keeps a symbol when its `visibility` on either side matches; `internal` and `all` are the other values, and only they show `structure` rows, which change nothing outside the symbol's visibility boundary. The default output is therefore the interface change list: exported symbols added, removed, or changed in signature. Each row carries kind, owner, name, both shape strings when they differ (the public shapes for `signature` rows, the private ones otherwise), a shape diff for `signature` and `structure` rows, and both file paths.

**Shape diff rendering.** A `signature` or `structure` row shows what changed in the shape, not only that it changed. Each class diffs the shapes of the layer it names: a `signature` row the public shapes (`public_shape`, where a struct shows its exported fields and `opaque`), a `structure` row the private (full) shapes (`shape`). The two canonical renderings are line-diffed with Myers, treating lines that differ only in whitespace (gofmt realignment) as equal. Within a changed hunk, the i-th removed line and the i-th added line form a replaced pair when their token diff shares at least one non-blank token; short equal runs between edits are folded into the edit, so a changed tail reads as one replacement. Tokens are split by the root's tokenizer (`symboldiff.Tokenizer`): a Go root's lines by `go/scanner` (`go`), an external root's language-neutrally (`text`: identifiers, which may start with `@`, `#`, or `$`, numbers, quoted strings and identifiers, and runs of other non-space characters). The plain form prints unchanged lines with two spaces, removed lines with `- `, and added lines with `+ `; the rich forms print a replaced pair as one `~ ` line through clicky `api.Text`, removed tokens red and struck through, added tokens green and bold, which is ANSI in a terminal, `~~removed~~` and `**added**` in markdown, and clicky's `<s>` and `<strong>` in HTML. JSON carries the structured form: `shape_diff` is a list of lines `{op, text, paired, tokenizer, tokens: [{op, text}]}`, where `op` is `equal`, `delete`, or `insert`, a paired line names the `tokenizer` (`go` or `text`) its tokens were split by, and a paired delete line's tokens are its equal and deleted runs while the paired insert line's are its equal and inserted runs. The same renderer serves the `removed`-plus-`added` grouping of a parameter-type change, diffing the old identity's shape against the new one so a type change reads as one signature edit. The package-level `export_shape_hash` pre-check is not applied, because skipping a package would hide its exported `body` rows and line counts ([diff.md](diff.md)). A `syntax` document on either side has no ids, so its symbols are matched by `key` and can only be classified `added`, `removed`, `body`, or `moved`; the row is marked `syntax`.

**Line attribution (b).** For each changed file, read both commits' bytes from Git (`git cat-file` on the blob at that commit in a registered checkout of the root) and verify each against the source revision's `content_hash`; a mismatch or a missing checkout fails the diff for that file with the reason, and the symbol diff for that file is still reported. Each side's document gives symbol extents in bytes. The file is partitioned into segments: one per outermost symbol extent, plus the gaps between them, which form a single `(file scope)` segment covering package clause, imports, comments, and anything not inside a declaration. Segments are paired by symbol id (or by `key` for `syntax` documents), and the gap segments are paired with each other. Each pair is line-diffed independently (Myers over lines), which yields `+added -removed` per symbol exactly, because a change inside one declaration cannot be attributed to another. A symbol present on one side only contributes all of its extent lines as added or removed. A `moved` symbol is diffed across files and reported under the destination file with the source path noted.

Per-file totals are the sums of their segment pairs, and per-package totals the sums of their files, so `store.go +14 -5` equals the sum of its symbol rows plus its file-scope row.

```text
example.org/service/invoices                          +14 -5
  invoices/store.go                                   +14 -5
    Store.Save          signature   +10 -3
      - func (s *Store) Save(ctx context.Context, inv Invoice) error
      + func (s *Store) Save(ctx context.Context, inv Invoice, opts ...SaveOption) (Receipt, error)
    Store.load          body        +4  -2
    (file scope)                    +0  -0
  invoices/model.go                                   +6  -6
    Invoice             signature   +1  -1
        type Invoice struct {
          ID       InvoiceID
      -   Total    int
      +   Total    Money
      +   Notes    string
        }
    Invoice.Total       added       +6  -0   func (i Invoice) Total() Money
    Invoice.total       removed     +0  -6   func (i Invoice) total() Money
```

In a terminal the `Store.Save` pair renders as one line with token marks rather than two full lines: the removed `) error` tail is red and struck through, and `, opts ...SaveOption) (Receipt, error)` is green and bold, so the reader sees the added variadic parameter and the new result tuple without comparing the lines by eye. In markdown the same pair is `func (s *Store) Save(ctx context.Context, inv Invoice~~) error~~**, opts ...SaveOption) (Receipt, error)**`. The plain-text form above is what `--format text` and non-TTY output print.

With `--visibility exported` the `Store.load` and `Invoice.total` rows are hidden; the file totals then state that hidden rows exist rather than silently summing to less than the file's diff.

**Coverage.** A `partial` file on either side still diffs the symbols it proved; the row is marked `partial` so a missing symbol is not read as removed. An `excluded` file is listed as excluded with its line diff attributed entirely to file scope.

**Cost.** Two content-free membership derivations, two effective-symbol walks, the definition postings of the changed documents, and batched content loads of the documents chosen above. A sibling file of a re-keyed package keeps its document when its rendering did not change, so changed files are exactly the files whose documents differ. Git reads are bounded by changed files.

## Index inventory

All indexes are listed with their tables above. Named secondary indexes, in HCL naming: `locations_parent_idx`, `snapshots_location_started_idx`, `snapshots_base_idx`, `snapshots_root_revision_idx`, `source_deltas_revision_id_idx`, `symbols_lookup_idx`, `symbols_search_idx`, `documents_source_idx`, `symbol_postings_symbol_idx` over `(symbol_handle, role, root_ordinal, document_ordinal)`, `symbol_deltas_handle_idx` over `(symbol_handle, snapshot_ordinal)`, `document_deltas_document_idx` over `(document_ordinal)` (the reverse lookup a document delete's foreign key check needs), `package_coverage_input_idx`. Unique indexes are named `<table>_<columns>_key`; among them `symbols_handle_key` is the B-tree that handle ranges scan (selector candidates, and the largest handle of a bucket when a local is allocated), and `modules_ordinal_key`, `snapshots_ordinal_key`, and `documents_ordinal_key` are the targets of the posting and delta foreign keys. `symbols.owner_id` still has no index of its own: a lookup by owner alone scans `symbols`, and owner chains are loaded by id in batches instead.

`search_name` is the symbol's `name` lowercased and restricted to `[a-z0-9]`, with every other character (including `_`) removed; a name with none of those characters, such as `_`, stores an empty `search_name` and is found only by exact name. `storage.SearchName` is the one implementation, shared by the indexer and the query layer. A prefix search is then `search_name >= ? AND search_name < ?`, which uses the B-tree on both engines. The upper bound increments the prefix within the ordered alphabet `0-9` then `a-z` with carry (`9` becomes `a`; a trailing `z` is dropped and the character before it increments), and a prefix of only `z` has no upper bound. The bound never leaves the alphabet, because a punctuation byte sorts below digits and letters under glibc and ICU collations and would make the range empty. The query layer still keeps only the rows whose `search_name` starts with the prefix, so a collation that orders the range differently can only over-fetch. Because `search_name` and `visibility` are derived, publication upserts a symbol on conflict of `id` and refreshes both columns from the incoming row, so a reindex after a normalization change rewrites existing rows; `canonical_key` and the other identity facts are still verified against the stored row. Column collations and operator classes are outside the portable subset, so a general `LIKE 'prefix%'` must not be relied on. Qualified input such as `Store.Save` is split by the query layer: resolve owners by `search_name = 'store'`, then filter children by `owner_id`. Substring and fuzzy search need a separate design.

## Query and update examples

**References to B at every head.** Resolve B through `symbols_lookup_idx`; a selector matching several symbols returns candidates first. Map B's id to its handle once per query. For each selected location head, derive its active document ordinals. Then read `symbol_postings_symbol_idx` for `(handle(B), 1, root_ordinal)` and intersect with the active set; the query layer reads the root's posting range when it holds no more rows than the active set (bounded at one row past it), and otherwise probes the posting key with the active ordinals in batched `IN` lists. Load the matching documents, filter occurrences with `symbol = B`, and return one row per occurrence with path, range, role, and enclosing symbol, mapping handles back to ids. Declaration locations come from the same intersection with role 0 (`definition`); before reading those postings, `DefinedSymbols` tells which snapshots define B at all, and a root none of whose scopes does is skipped. A same-location declaration is preferred for display and other heads remain visible as candidates. Reference rows are never multiplied by the number of declaration locations.

**References in a historical snapshot.** Identical, with the active set derived for that snapshot. A `syntax` or `excluded` package in scope is reported as such so an empty result is not mistaken for proven absence.

**Callers of B, interface-aware.** Each scope's [implements facts](#implements-facts) for interface I give the concrete types that satisfy I. Callers of a concrete method `T.M` are the references to `T.M` plus the references to `I.M` for every I that T implements, when the caller asks for dispatch-inclusive results. Dispatch through an interface the facts do not consider is not proven.

**Callees of A.** Load A's defining document (the `definition` posting of `handle(A)` intersected with the active set) and return occurrences whose `enclosing` is A and whose role is `call`.

**Nodes and browse.** The existing `nodes where …` predicates and the explorer read `symbols` entries from active documents, typed or syntax, so the current AST-only behaviour is preserved for packages that do not type-check.

**Typed selectors.** A `pkg:` selector, or a symbol selector qualified by a package path, reads its candidates through the handle ranges of the registered packages it can match; any other selector reads each admitted root module's whole range. The ranges are merged and ORed into `handle BETWEEN` conditions over `symbols_handle_key`, and the candidates are then kept only where a selected snapshot of their own root defines them (`DefinedSymbols`).

**Name search and resolution.** Range-scan `symbols_search_idx` (spelling resolution and suggestions both take this path), keep symbols that a selected snapshot defines (`DefinedSymbols`, from symbol deltas) or that an active document references (postings) or a scope's type implements (implements facts), both read only for the symbols no snapshot defines, and rank by kind and module.

**Diff.** `uir diff <from>..<to> --root example.org/service` lists exported symbol changes; `--visibility all` includes internal symbols; `--stat` adds per-file and per-symbol line counts and requires readable Git blobs.

| Edit | Symbols | Documents, postings, and symbol deltas | Diff classification |
| --- | --- | --- | --- |
| Insert a comment above a use of B | Unchanged | Package input hash changes and the package is re-rendered; the edited file gets a new document (its ranges moved) and one document delta, its siblings keep theirs; no symbol delta, because `content_hash` ignores comments | `body` (layout only, with `--stat`) if inside a symbol's extent, otherwise file scope `+1 -0` |
| Add a second call from A to B | Unchanged | A new document for A's file; posting `(doc, B, reference)` count becomes 2; `set` for A with a new content fingerprint | `body` on A |
| Change A's parameter name | Unchanged | A new document for A's file; `set` for A with new public and private fingerprints and the same content fingerprint; the export shape is unchanged, so no dependent is re-extracted | `signature` on A (names are in the shape, not the identity) |
| Change A's parameter type | New symbol for A; old retained | A new document for A's file and, if A is exported, for every dependent file that names A; `delete` for old A, `set` for new A | `removed` old A, `added` new A, grouped |
| Move B to another file in the same package | Unchanged | New documents for both files; B's `definition` posting moves; no symbol delta, because B's fingerprints are equal | `moved` |
| Change an exported return or field type | Identity may remain | Export shape changes; every directly importing package is re-rendered, and only its files whose documents change get new ones; `set` for the changed symbol | `signature` |
| `go get` bumping a dependency | Unchanged | New snapshot with zero source deltas; importing packages are re-rendered, and keep their documents unless their rendering changes; their symbols get deltas only if their fingerprints change | No symbol rows; `go.sum` is a changed file with file-scope lines |

**Cost note on package granularity.** A package's input hash covers all of its files, so editing one file still re-renders every file of the package, but publication stores only the documents whose rendering changed: one document and one document delta for a one-file edit whose siblings render as before. Rendering, not storage, is now what package granularity costs; moving the input comparison ahead of `packages.Load` is [Phase 3 of the incremental snapshot plan](incremental-snapshot-plan.md#phase-3-incremental-go-extraction).

## Expected size and cost

Let `F` be files per module, `P` packages, `S` snapshots, `c` files re-extracted per snapshot, `k` distinct symbols mentioned per file, and `L` active location heads.

- Documents: one row per `(path, content_digest)`. History grows by `c` documents per snapshot, each a few kilobytes; this replaces the projection column rather than adding to it.
- Document deltas: one row per path whose bound document changed per snapshot, plus every path for a snapshot without a base.
- Postings: `k` rows per document, typically 3 to 5 times fewer than occurrences in real files, each five integers (document ordinal, root ordinal, handle, role, count) plus two index entries.
- Package coverage: `P` rows per snapshot, `O(S × P)`.
- Symbols: one row per distinct identity ever observed, retained, each with its handle.
- Symbol registry: one `symbol_modules` row per module key and one `symbol_packages` row per package path ever observed.
- Symbol deltas: one row per symbol added, changed, or removed per snapshot, plus every defined symbol for a snapshot without a base.
- Membership: two recursive CTEs (source and document deltas) plus `P` package rows plus `F / 256` batched ordinal lookups per snapshot derivation. Symbol membership is one recursive CTE over the deltas.
- Reference lookup: one derivation, one posting range scan bounded by `(handle, role, root ordinal)`, then document reads equal to the number of matching files. No `O(L × R)` posting tables exist.
- Diff: two content-free derivations, two symbol-delta walks, definition postings of changed documents, document reads only where the output needs shapes, keys, or line counts, Git reads for changed files, and in-memory line diffs per symbol pair.

Using the earlier illustration (100 modules, 500 files, 10,000 occurrences per module, 1,000 snapshots, one 20-occurrence file changing per snapshot, 5-file packages): about 550,000 documents, roughly 8 million posting rows at 15 distinct symbols per document, 5 million package coverage rows, and no occurrence, checkpoint, head, or diff rows. The occurrence-row design stored about 3 million occurrence rows plus 1 million head postings plus 800,000 checkpoint pointers under an assumption that ignored package re-typing. With realistic files of 200 to 500 occurrences and 60 to 100 distinct symbols the posting design stores four to five times fewer rows; with the toy 20-occurrence file it does not, and its saving is row width and the absence of position rows. These are algorithmic expectations, not measured latency guarantees; step 8 below measures them.

**Measured** (step 8, [benchmarks](benchmarks.md), SQLite and PostgreSQL 16 on this repository and `flanksource/commons`):

- Documents average 145 KB, which is 1.4 KB per declared symbol and 235 B per occurrence. That is far above the "few kilobytes" assumed above, and documents are 66 to 72 % of the database.
- A single-file body edit re-stores the whole package: 8 to 10 documents, 790 to 880 postings, and 1.4 to 1.7 MB on SQLite. After 200 such commits the commons database grew from 17.5 MB to 350 MB, with 1,708 documents and 182,568 postings.
- Postings cost about 490 B each in SQLite once both indexes are included. Under compact handles they cost 73 B on SQLite and 165 B on PostgreSQL (cold five-checkout corpus, [compact symbol handles](symbol-compact-ids.md)).
- The recursive CTE over a 200-link chain takes 1 ms. Posting lookups are covering range scans of `symbol_postings_symbol_idx` on both engines.
- Per head, the membership derivation's real cost is reading every active document's `content` (about 15 MB). That motivates a content-free membership lookup, not the phase-2 head table. `ActiveDocuments` now omits `content` unless asked; the diff uses that, while the query layer still loads content for every active document.
- Unchanged runs now skip type-checking: 3.3 to 4.5 s before, 0.14 to 0.67 s after. Other runs are dominated by the 4 to 15 s `go/packages` load.

Discovery still reads and hashes all included files on each run. Extraction runs through `go/packages` on changed packages and their dependents and completes before the publication transaction opens: the transaction allocates handles for new symbols and ordinals for new documents and the snapshot, writes symbols, documents, postings, package rows, the snapshot row, and its symbol deltas, then advances the head with the existing version check. SQLite's single connection is never held across type-checking.

## Phase-2 option: head materialization

If measured head queries across many locations are too slow because each head derivation repeats the CTE and key lookups, add `head_documents (location_id, root_id, path_key, document_id)` with PK `(location_id, path_key)`, replaced for changed paths in the publication transaction. It holds `O(L × F)` small rows, not `O(L × R)`, and reference queries join it directly with postings. The criterion for adding it is a benchmark on a real workspace showing derivation above a fixed budget per head; it is not part of the initial schema.
