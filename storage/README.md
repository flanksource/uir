# UIR storage design

`storage.UirDB` owns the GORM connection and applies the embedded Atlas HCL through `commons-db/migrate`. GORM models map rows; `AutoMigrate` does not own the schema. The seven base tables are specified by [04_module_roots.hcl](migrations/04_module_roots.hcl) and [05_source_deltas.hcl](migrations/05_source_deltas.hcl), the four symbol-index tables by [06_symbol_index.hcl](migrations/06_symbol_index.hcl), and the handle registry and symbol deltas by [07_symbol_handles.hcl](migrations/07_symbol_handles.hcl); [symbol index storage](../docs/symbol-index-storage.md) is their design, and [compact symbol handles](#compact-symbol-handles) below describes the surrogate keys. The [Facet ERD](../docs/uir-gorm-erd.tsx) shows their keys and references. The integration tests assert, on both engines, that every model's columns and nullability match the migrated table and that every named index, foreign key, and check exists.

## Opening and cutover

The DSN selects PostgreSQL (URL or keyword DSN) or SQLite (`sqlite://` URL or plain `.db` path). `Schema` selects a PostgreSQL schema and defaults to `public`; SQLite rejects a non-default schema. In-memory SQLite is rejected because migration and application connections would not reliably share state. SQLite enables foreign keys, WAL, a five-second busy timeout, and one open connection. PostgreSQL is the shared-writer option. Migration and a connection ping must succeed before `UirDB` returns.

```go
database, err := storage.UirDB(ctx, storage.DBOptions{DSN: "./state/uir.db"})
if err != nil {
    return err
}
sqlDB, err := database.DB()
if err != nil {
    return err
}
defer sqlDB.Close()
```

Opening an existing database **discards the index of every previous schema generation**. `UirDB` opens the connection, discards a pre-handle index, applies the current schema, and then discards the `uir_`-prefixed generations.

**Pre-handle generation.** A database built before [compact symbol handles](#compact-symbol-handles) has the same unprefixed table names, but `modules`, `snapshots`, and `documents` have no `ordinal`, `symbols` has no `handle`, and `symbol_postings` is keyed by `(document_id, symbol_id, role)`. The current schema cannot be reconciled onto those tables without rewriting their rows, so this cutover runs **before** migration. Such a database is recognised by `modules` existing without an `ordinal` column: one catalog query (`sqlite_master` and `pragma_table_info` on SQLite, `pg_class` and `pg_attribute` in the `Schema` on PostgreSQL), which is the only cost it adds when opening a current or empty database. In one transaction `UirDB` then:

- **Discards the index.** It drops `symbol_postings`, `package_coverage`, `documents`, `symbols`, `source_deltas`, `source_revisions`, `location_heads`, and `snapshots`, child first, and migration creates them again, empty. No index rows are imported. `location_heads` goes with them because every head references a snapshot.
- **Keeps the registrations.** `locations` and `primary_locations` are unchanged in the current schema and keep their rows. `modules` keeps its rows and gains `ordinal`, numbered densely from 1 by `created_at`, then `root_key`. On PostgreSQL that is `ADD COLUMN`, an `UPDATE` from `ROW_NUMBER()`, and `SET NOT NULL`; migration then adds the unique key and the check. SQLite can add neither a `NOT NULL` column nor a check to a populated table, so the cutover rebuilds `modules` as `04_module_roots.hcl` declares it (the `CREATE TABLE` commons-db would emit), copies the rows with their ordinals, and renames it into place; migration then adds the two unique indexes.

Run `uir reindex --all` afterwards; `UirDB` logs a warning saying so. Every registered location is headless, so reindex indexes it in full: a location's first snapshot bases on the primary location's head, and on none when the primary has no head either. Until a root is reindexed, `uir list` and `uir get` show it with no snapshot, and unscoped readers skip it with a warning, while an explicit root or checkout selection still fails with "root … is registered but not indexed; run `uir reindex` on its checkout". On SQLite the cutover runs with foreign key enforcement suspended on its one connection and restored afterwards: enforcement makes `DROP TABLE symbols` check every row against the unindexed self-reference `owner_id` (about three minutes on the fixture corpus, a few seconds without), and would refuse to drop the old `modules`, which `locations` references. The same refusals apply as below, to the discarded tables: SQLite checks every other table for a foreign key to one of them, PostgreSQL refuses to drop a table another object depends on, and either failure rolls the whole cutover back and leaves the pre-handle tables and their rows unmigrated. Reopening the rebuilt database finds `modules.ordinal` and changes nothing. `OpenReadOnly` runs the same detection and fails with "database predates compact symbol handles; open it read-write once or run uir reindex". The test fixture `testdata/prehandle/` holds that generation's 04–06 HCL.

**`uir_`-prefixed generations.** After applying the current schema, `UirDB` drops only the `uir_`-prefixed module-root generation (`uir_source_deltas`, `uir_module_location_heads`, `uir_module_primaries`, `uir_source_revisions`, `uir_module_snapshots`, `uir_module_locations`, `uir_module_roots`) and the older project generation (`uir_relationships`, `uir_fields`, `uir_node_locations`, `uir_nodes`, `uir_sources`, `uir_roots`, `uir_project_heads`, `uir_snapshots`, `uir_projects`), child first, in one transaction. No rows are imported: run `uir reindex` on each checkout to rebuild the index. Back up an old database *before* opening it with this version if its history matters. PostgreSQL refuses a drop blocked by an external dependency; SQLite checks nonlegacy tables for foreign keys to legacy tables and refuses the cutover. Initialization then fails, and every legacy table remains, instead of silently removing dependent data. Migration and cutover are separate transactions: if cutover fails, the new schema may already exist while legacy tables remain. Reopening a successfully cut-over database has no legacy tables left to drop.

The HCL files are one schema source for both targets. PostgreSQL uses canonical `uuid`, `jsonb`, and `timestamptz`; the SQLite adapter in `commons-db/migrate` maps them to text, JSON-valid text, and datetime while preserving keys, checks, and indexes. The `commons-db/migrate/README.md` guide defines the portable HCL subset and incompatibilities. UIR permits transactional SQLite rebuilds for compatible constraint changes, including widening `symbol_postings_role_check` from roles 0–2 to 0–3 while preserving postings. Drops, renames, and type changes remain refused. The compact-handle columns (`modules.ordinal`, `snapshots.ordinal`, `symbols.handle`, `documents.ordinal`) and the reshaped `symbol_postings` were added to 04 and 06 in place; a database that holds rows under the previous shape has its index discarded and its registrations numbered by the pre-handle cutover above rather than migrated.

## Relational hierarchy

| Table / GORM model | Identity | Responsibility |
| --- | --- | --- |
| `modules` / `ModuleRoot` | unique `root_key` from `go.mod` | Logical Go module, independent of checkout path. |
| `locations` / `ModuleLocation` | unique `(root_id, canonical_path)` | Physical checkout or nested module location, with optional parent, mount path, kind (`module`, `git`, or `git-submodule`), and repository URI. |
| `primary_locations` / `ModulePrimary` | one row per root | First registered location, used by default node queries and browse. |
| `snapshots` / `ModuleSnapshot` | UUID and unique `ordinal`; `(root_id,id)` and `(location_id,id)` for scoped references | Published index run for one root and location, optionally based on another snapshot of that root, with its worktree state, context hash, and coverage. |
| `location_heads` / `ModuleLocationHead` | one row per location | Snapshot published for that checkout, with compare-and-swap version. |
| `source_revisions` / `SourceRevision` | unique `(root_id,path_key,content_hash,package_path)` | Reusable content-addressed file version: hash, package, and size, with no extracted facts. |
| `source_deltas` / `SourceDelta` | `(snapshot_id,path_key)` | `set` to a revision of that path or `delete` tombstone. |
| `documents` / `Document` | unique `(root_id,path_key,input_hash)` | The facts extracted from one file version under one package input hash: a typed (`indexed` or `partial`) document from `go/packages`, a `syntax` document from the Go AST extractor when the package could not be loaded, or an empty `excluded` document. |
| `package_coverage` / `PackageCoverage` | `(snapshot_id,package_path)` | Per snapshot, the input hash that selects each package's documents, its coverage, its export shape hash when `indexed`, its file count, and its diagnostics. |
| `symbols` / `Symbol`, `symbol_postings` / `SymbolPosting` | `id` and unique `handle`; `(document_ordinal,symbol_handle,role)` | Canonical symbol identities, global and never cascaded, each with a database-local handle, and the inverted index from each symbol handle to the documents that define, reference, or implement it. |
| `symbol_modules` / `SymbolModule`, `symbol_packages` / `SymbolPackage` | `number`, unique `module_key`; `(module_number,number)`, unique `(module_number,package_path)` | The numbering a handle packs: module keys and, per module, package paths. |
| `symbol_deltas` / `SymbolDelta` | `(snapshot_ordinal,symbol_handle)` | Per snapshot, how its defined-symbol set differs from its base's. |

`root_key` is the full module path, not a display basename. Canonical checkout path is physical location, not logical identity. Multiple worktrees and clones of one module share a root but keep separate heads. A source revision belongs to one root; reuse across its checkouts is intentional, but different module paths never share one row. The hash covers source bytes; `package_path` prevents reuse under a different interpretation, and extraction is versioned by the document key instead. The indexer supplies module-relative source paths, and the content reader rejects absolute or traversal paths; the HCL itself checks only that a stored path is nonempty.

A snapshot references one root and one location in that root. A new location may base its first snapshot on the current primary head; subsequent runs base on its own head. Composite foreign keys enforce root agreement for locations, snapshots, bases, deltas, revisions, and documents; a head references its snapshot through `(location_id, snapshot_id)`, so it cannot point at another location's snapshot, and a delta or document references its revision through `(root_id, path_key, revision_id)`, so it cannot point at another path's revision. A snapshot row exists only once its publication committed, so there is no snapshot state and `completed_at` is always set.

An effective source set is not a full physical copy. `storage.EffectiveSources` resolves the whole base chain in one recursive CTE (`WITH RECURSIVE` plus `ROW_NUMBER() OVER (PARTITION BY path_key ORDER BY depth)`, identical on SQLite and PostgreSQL) that returns the newest delta for each path, so the statement count does not grow with history depth; tombstones drop their path, and the referenced revisions are then loaded in batches of 256 and must match the delta's root and path. The walk is capped at 100,000 base links: a chain that reaches the cap with a base still pending is reported as a base cycle, a dangling base or a chain spanning roots fails, and a missing snapshot fails. `storage.ActiveDocuments` derives a snapshot's `path_key → document` membership from it: the snapshot's `package_coverage` rows give each package's input hash, and each path's document is looked up by `(root_id, path_key, input_hash)` in batches; a missing document, a coverage row whose file count disagrees with the effective sources, or a document describing another revision is an error. `storage.DecodeDocument` validates a document against its revision before the indexer writes it and whenever a reader loads it, by the rules of its coverage: a `syntax` document has no ids; a typed document has an id and shape hash on every proven declaration, a role and either a symbol or a note on every occurrence, and enclosing ids declared in the same document; an `excluded` document is empty and states why. Document JSON preserves each declaration's canonical id, kind, visibility, shape, hashes, implemented interfaces, structured identifier, parent/slot/order, payload, semantic hash, name and extent ranges, optional field detail, and every identifier occurrence; these are **not** separate GORM node or relationship rows. Historical queries read the saved documents even after a later head changes or removes a file. Raw source bytes are **not** stored; source viewing verifies a local file's hash or a pinned Git blob against the saved hash, and fails if neither matches.

## Typed extraction

`indexer` loads each module root once through `golang.org/x/tools/go/packages` (`NeedName|NeedFiles|NeedSyntax|NeedTypes|NeedTypesInfo|NeedImports|NeedDeps|NeedModule`) in the module directory, under the `go env` build variant the configuration hash records, with pattern `./...` and test variants when tests are included. The whole dependency graph is type-checked from source. Every root file's bytes as parsed must hash to the discovered content hash, otherwise the run fails because the file changed while indexing. Extraction runs entirely before the publication transaction opens.

Each discovered package gets one coverage. A file that build constraints exclude, or whose directory builds no package, is `excluded`, and a package whose every file is excluded is `excluded`. A parse error in a package's own files fails the run, as the AST extractor did. A `go list` error on the package itself (for example two package names in one directory), a variant without type information, or a file the load did not type-check makes the package `syntax`: its files keep the AST extractor's documents, with the load diagnostics attached, and have no postings. Any other error (type errors, an import that cannot be resolved) makes it `partial`: only proven facts are recorded, and the diagnostics are stored on the package row and on the documents they are positioned in. Otherwise it is `indexed`. A snapshot's coverage is the weakest of its packages' among `indexed`, `partial`, and `syntax`; `excluded` packages were deliberately not extracted, so a snapshot is `excluded` only when every package is, and `indexed` when it has no packages. Its `diagnostics` list, per package that is not `indexed`, the coverage and diagnostics.

Canonical identities, visibility, shapes, and hashes follow [symbol index storage](../docs/symbol-index-storage.md#hashes-and-identities). A symbol's `search_name` is `SearchName(name)`: the name lowercased and restricted to `[a-z0-9]`, empty when the name has none of those characters. Publication upserts symbols on `id`, refreshing `search_name` and `visibility`. `package_coverage.export_shape_hash` is set only for an `indexed` package. For the importers' input hashes every direct import still presents an export shape: the real one for a workspace package (the module's own, a `go.work use` module, or a directory `replace`) that type-checked without errors; for a workspace package with errors, whose shape is unproven, a digest of its package path, its files' names and content hashes, and its imports' export shapes, so any edit to it still re-extracts its importers; `H(module path, version, toolchain)` for a module-cache package (the replacement's path and version for a module replace); `H("std", toolchain)` for the standard library; and a digest of the path alone for an import no module provides.

## Compact symbol handles

The SHA-256 symbol id remains the identity: documents, canonical keys, export shape hashes, and input hashes are unchanged, and nothing outside this database ever sees a handle. Inside it, postings and symbol deltas store compact surrogates instead of 64-character ids and UUIDs.

- **Handle.** `symbols.handle` is a unique `bigint` in the H64a layout of [`storage/symbolhandle`](symbolhandle/handle.go), most significant bit first: `0 | module 11 | package 16 | visibility 1 | kind 3 | local 32`. Visibility is 1 for `exported`; kinds are `package` 0, `type` 1, `func` 2, `method` 3, `field` 4, `var` 5, `const` 6, `builtin` 7. The sign bit is always zero, so handles sort by module, package, visibility, kind, then local, and `symbolhandle.PackageRange`, `VisibilityRange`, and `BucketRange` turn "every symbol of a package", "every exported symbol of a package", and "every exported func of a package" into one inclusive B-tree range. `Pack` fails naming the field that does not fit; `Unpack` fails on a negative handle.
- **Registry.** `symbol_modules` numbers module keys: `''` (builtins) is 0, `std` is 1, every other key the next number from 2, up to 2047. `symbol_packages` numbers each module's package paths from 0, up to 65535. Check constraints enforce both ranges and the reserved numbers.
- **Locals.** A new symbol takes the next local of its (module, package, visibility, kind) bucket: 0 in a package the same allocation registered, otherwise one past the bucket's largest stored handle, read by `ORDER BY handle DESC LIMIT 1` over the bucket's range of `symbols_handle_key`. No sequence or counter table exists. `storage.AssignSymbolHandles` allocates the rows it is given in their order and missing registry numbers in key order, so replaying the same publications produces the same handles. A stored symbol keeps its handle, and a stored handle that disagrees with the row's module, package, visibility, or kind is an error; since visibility is in the handle, a symbol whose derived visibility changes cannot be re-published and fails loudly.
- **Ordinals.** `modules.ordinal` (`integer`), `snapshots.ordinal` (`bigint`), and `documents.ordinal` (`bigint`) are unique, dense, database-local numbers from 1, allocated as one past the current maximum inside the publication transaction (`storage.NextModuleOrdinal`, `storage.NextSnapshotOrdinal`, `storage.NextDocumentOrdinal`; `storage.CreateModuleRoot` and `storage.CreateSnapshot` assign the ordinal themselves, `storage.CreateDocument` takes one the publisher assigned). A publication that loses the race for a document key to another writer leaves a gap in document ordinals; nothing depends on density.
- **Postings.** `symbol_postings (document_ordinal bigint, root_ordinal integer, symbol_handle bigint, role integer, occurrence_count integer)`: role is 0 `definition`, 1 `reference`, 2 `implements`, or 3 `embeds` (`storage.PostingRole`). The primary key `(document_ordinal, symbol_handle, role)` serves the per-document probe and the document cascade; `symbol_postings_symbol_idx (symbol_handle, role, root_ordinal, document_ordinal)` serves the per-symbol range. The root ordinal is the discriminator a reference lookup filters on, so a range over one root never reads other roots' postings; the publisher takes it from the document's root. Foreign keys reference `documents(ordinal)` and `modules(ordinal)` with `CASCADE` and `symbols(handle)` with `NO ACTION`.
- **Concurrency.** Every allocation reads the current maximum inside the publication transaction and relies on the unique keys to reject a duplicate. On PostgreSQL a concurrent publisher that took the same number makes the insert block and then fail with a unique violation (or a deadlock or serialization failure); those SQLSTATEs (`23505`, `40P01`, `40001`) at an allocating insert, and a symbol a concurrent publisher inserted with a different handle, are wrapped as `storage.ErrAllocationConflict`. `storage.RetryAllocationConflicts` runs the publication transaction again from the start, at most `storage.AllocationAttempts` (3) times; `indexer.IndexModules` and `IndexRevision` publish through it. Any other error is returned at once, and the head compare-and-swap still fails a publication whose head moved. SQLite has one writer, so it never retries.

### Symbol deltas

`symbol_deltas (snapshot_ordinal bigint, root_ordinal integer, symbol_handle bigint, operation text, shape_fp bigint?, body_fp bigint?)` records, per snapshot, how its **defined-symbol set** differs from its base's. The defined set is every declaration with a canonical id in the snapshot's active documents; syntax declarations and unproven declarations of a partial document have no id and no handle and are never in it, so a package falling back to `syntax` deletes its symbols from the set. A fingerprint is the first eight bytes of the `shape_hash` or `body_hash` as a signed int64 (`storage.SymbolFingerprint`). `set` carries both fingerprints and `delete` neither, which `symbol_deltas_operation_check` enforces. The primary key is `(snapshot_ordinal, symbol_handle)`, and `symbol_deltas_handle_idx (symbol_handle, snapshot_ordinal)` serves one symbol's history. Foreign keys reference `snapshots(ordinal)` and `modules(ordinal)` with `CASCADE`, so the rows go with their snapshot or root, and `symbols(handle)` with `NO ACTION`. Unlike source deltas, no composite key ties the root ordinal to the snapshot's root; the publisher takes them from the snapshot it just created and that snapshot's root. The base-chain walk carries each snapshot's ordinal, so `EffectiveSymbols` and `DefinedSymbols` join the deltas on it.

The publisher writes them in the publication transaction. A path's active document is keyed by its package input hash, so the publisher compares the base's and the new snapshot's keys and reads only the documents of paths whose key differs: the base's stored documents for those paths, and the extraction for the new side. Unchanged documents are never read. Declarations are grouped by id across those documents; a symbol present on both sides with equal fingerprints, such as one that moved between two changed files, gets no row, a new or changed one gets `set`, and one only the base declared gets `delete`. A snapshot without a base records every defined symbol as `set`; a dependency bump that re-keys no document records nothing.

This is sound because a canonical id includes its Go package, a package's files share one directory and one input hash, and all of them get new documents together: a symbol cannot lose a declaration in a changed file while keeping another in an unchanged one. The publisher checks that every id it reads is declared in one package directory and fails otherwise. One id can have several declarations only because every `func init` of a package shares one canonical id (gavel TODO 34ea4d17); `storage.FoldDeclarations` combines them order-independently, keeping a single declaration's fingerprints and otherwise hashing the distinct pairs sorted by shape then body, shapes and bodies separately, so an init body edit changes only the folded body fingerprint.

### API for query and diff consumers

| Function | Returns |
| --- | --- |
| `EffectiveSymbols(ctx, db, snapshotID)` | `[]EffectiveSymbol{Handle int64; ShapeFP, BodyFP *int64}` sorted by handle: one recursive CTE over `symbol_deltas` along the base chain, the newest row per handle, tombstones dropped. A base cycle (over 100,000 links), a dangling base, a chain spanning roots, and a missing snapshot are errors, as for `EffectiveSources`; so is a `set` row without fingerprints. |
| `DefinedSymbols(ctx, db, snapshotID, handles)` | The sorted, distinct subset of `handles` the snapshot defines: the `EffectiveSymbols` CTE restricted, before ranking, to IN batches of 256 handles, so its cost follows the handles asked about rather than the size of the snapshot. An empty list reads nothing; the chain errors are those of `EffectiveSymbols`. |
| `SymbolHandles(ctx, db, ids)` / `SymbolIDs(ctx, db, handles)` | `map[string]int64` / `map[int64]string`, in IN batches of 256; an unknown id or handle is an error. |
| `DocumentOrdinals(ctx, db, ids)` / `DocumentIDs(ctx, db, ordinals)` | `map[uuid.UUID]int64` / `map[int64]uuid.UUID`; unknown keys are errors. `Document.Ordinal` is also loaded with every document row, so `ActiveDocuments` already carries it. |
| `RootOrdinal(ctx, db, rootID)` | The root's `int32` ordinal; `ModuleRoot.Ordinal` carries it too. |
| `NextModuleOrdinal`, `NextSnapshotOrdinal`, `NextDocumentOrdinal` / `CreateModuleRoot`, `CreateSnapshot`, `CreateDocument` | One past the table's largest ordinal (1 when empty), read inside the publication transaction / the inserts that use them. `CreateModuleRoot` and `CreateSnapshot` assign the ordinal themselves and refuse a row that already has one; `CreateDocument` requires the ordinal the publisher assigned and reports whether it inserted the row, a repeat of the `(root_id, path_key, input_hash)` key being a no-op. A lost race for an ordinal is `ErrAllocationConflict`. |
| `ActiveDocuments(ctx, db, snapshotID, ActiveDocumentOptions{Content})` | The snapshot's `path_key → ActiveDocument` membership. Without `Content` each document row omits its content column, so a reader such as `symboldiff` finds the paths it needs first and loads only those with `DocumentContents`; the query layer passes `Content: true`. |
| `DocumentContents(ctx, db, ids)` | `map[uuid.UUID]JSON`: the content of the given documents, in IN batches of 256; an unknown id is an error. |
| `DefinitionPostings(ctx, db, ordinals)` | The `definition` postings of the given documents, sorted by document ordinal then symbol handle: a prefix scan of the posting primary key per batch of 256 ordinals. |
| `OwnedSymbols(ctx, db, handles)`, `OwnedSymbol.Identifier()`, `DeclarationIdentifier(packagePath, symbol, owners)` | Symbol rows with their owner names, outermost first, loaded by following `owner_id` in batches (an unknown handle or owner is an error), and the structured identifier the typed extractor gives a declaration. `DeclarationIdentifier` is the single rule: the indexer calls it for declarations the AST extractor does not project, and `Identifier()` applies it to a stored row. |
| `ParsePostingRole(name)`, `PostingRole.String()` | The role code of `definition`, `reference`, `implements`, or `embeds`, and back. |
| `SymbolFingerprint(hash)`, `FoldDeclarations(pairs)` | The fingerprint of a document's hash, and the fold of several declarations, to compare documents with deltas. |
| `symbolhandle.Pack`, `Unpack`, `PackageRange`, `VisibilityRange`, `BucketRange`, `ParseKind`, `ParseVisibility`, `ReservedModuleNumber` | Handle layout arithmetic; a range is `symbolhandle.Range{Low, High}`, inclusive, with `Contains`. `MaxModule`, `MaxPackage`, and `MaxLocal` are the field capacities. |

The query layer reads postings through these mappings (`query/module_index.go`): it resolves ids to handles, roles to codes, and each scope's active documents to ordinals, filters `symbol_postings` by `(symbol_handle IN, role IN, root_ordinal)`, and maps the rows back. Whether a scope defines a symbol comes from `DefinedSymbols`, remembered per snapshot for the query (`query/module_index_handles.go`), so a definition lookup skips a root whose every scope is known not to define the symbol, and name resolution reads `reference` and `implements` postings only for the symbols no scope defines. Typed selectors read their candidates through `symbolhandle` ranges (`query/selector_ranges.go`): a `pkg:` selector, or a symbol selector qualified by a package path, becomes the ranges of the matching registered packages, and any other selector each admitted root module's whole range, ORed into `handle BETWEEN` conditions over `symbols_handle_key` instead of a scan of `symbols`. `symboldiff` reads both sides' `ActiveDocuments` without content, classifies from `EffectiveSymbols` and the changed documents' `DefinitionPostings`, names rows it did not decode with `OwnedSymbols`, and loads only the documents its output needs with `DocumentContents`.

## Publication and adversarial boundaries

Discovery, type-checking, hashing, and document rendering complete before publication. Source-revision writes, symbol writes, document writes, and posting writes occur inside the `IndexModules` transaction, which then writes the snapshot row, its source deltas, package coverage, and symbol deltas, and advances the location head with a version check; a failed check rolls every row back. Symbols needed by new documents get their handles, are upserted owners first, and are re-read, and an existing row whose `canonical_key`, facts, or handle differ from the extraction's is a hard error (a different handle is an allocation conflict). Every document is validated by `DecodeDocument` against its revision before it is written; the extraction verifies that each typed entry's `kind` and `visibility` equal its symbol row and that every referenced id is a known symbol. Revisions, documents, and package rows are inserted with `ON CONFLICT DO NOTHING` and re-read, so a re-run never duplicates them; postings are written only by the publication that inserted their document, so an existing document's postings are skipped, not duplicated. A forced re-extraction whose document differs from the stored one under the same key fails, because a changed extractor needs a new indexer version. A syntax error or conflicting writer aborts that call. Selected external `go.work use` paths are indexed in a later call and therefore a separate transaction. A snapshot can have zero source deltas: a revision-only change, a dependency-manifest change, or a configuration change publishes one. A run avoids a new snapshot only when its Git revision, content-set hash, configuration hash, and context hash all equal the base snapshot's and `--force` is not used. The content-set hash covers the included `.go` files plus `go.mod`, `go.sum`, and the enclosing workspace's `go.work` and `go.work.sum` when present; those manifests are hashed, never stored as source revisions. The configuration hash covers the indexer version, test inclusion, and the `go env` build variant (`GOOS`, `GOARCH`, `CGO_ENABLED`, `GOVERSION`, build tags).

- **Multiple Git roots and clones:** Git repository boundaries and Go module boundaries are different. `go.mod` defines root identity; the nearest checkout supplies Git provenance. Two modules in one Git repository have distinct roots; two clones of the same module path share a root but retain distinct heads. Remote URI is diagnostic, not identity.
- **Nested modules and submodules:** discovery excludes a nested module's Go files from its parent scan. The child location stores its nearest parent and mount path; `.gitmodules` may mark a declared submodule. A nested module without `.git` is still separate. Not every Git submodule contains a `go.mod`, and not every nested `go.mod` is a submodule.
- **External workspace modules:** `go.work` can refer outside the selected directory. Interactive add asks whether to include them; non-interactive add must choose `--include-workspace-uses` or `--no-workspace-uses`. Discovery currently resolves every use path before that choice, so even an excluded missing path fails. Because publication calls are separate, inspect every returned result.
- **Moved checkout:** canonical path is the location key. Moving a directory registers a new location; it does not rewrite the old location or historical snapshots. The primary remains first-registered, so default queries can still point to an unavailable checkout. Select `--location` or `--snapshot` when needed. Automatic pruning and primary reassignment do not exist.
- **Branch switches and dirty trees:** snapshots describe indexed bytes, not branch names. A Git revision change creates a new snapshot even if the content set is unchanged. `worktree_state` includes changes under the module, its active workspace manifest, and linked local dependencies. Dirty Git-backed snapshots record `git-{commit}-dirty-{latest UTC file mtime}` in `revision` and keep the raw SHA in `git_commit`; `unknown` has an empty revision outside a Git checkout. `source_blobs` retain source bytes for dirty and non-Git snapshots, and source reads always verify the saved hash.
- **Symlinks and mounts:** input paths are canonicalized, directory symlinks are not traversed during discovery, and source viewing rejects paths escaping a registered location. The database cannot prove that a path still points to the same physical mount.
- **Call graph ambiguity:** typed documents record each call's canonical symbol id, and compact `<`, `>`, `<<`, and `>>` queries read those edges from active documents. Ambiguous spellings return candidates. Known interface dispatch through a receiver's recorded implementations is included; `syntax` packages, which have no ids or postings, and dependencies outside indexed roots prevent a sound whole-program graph. Unresolved call locators remain in documents but have no canonical query edge.
- **Retention and read cost:** snapshots, dependency edges, source blobs, source revisions, and documents are retained; compaction and garbage collection are not implemented. Documents are keyed by package input hash, so editing one file re-extracts and stores a new document for every file of its package. Long base chains cost more to reconstruct, and browse currently materializes all nodes in a snapshot. Do not delete a base snapshot while descendants reference it. Pre-existing snapshots have a null `dependency_set_hash` and report dependencies as not captured.

See [module indexing](../docs/module-indexing.md), [querying](../docs/query.md), and [serving](../docs/serve.md) for the operational contracts. HCL and integration tests are the executable schema specification.
